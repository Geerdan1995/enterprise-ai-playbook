# 附录K 解决方案工具箱——三十五个案例的解法速查
*Appendix K: A Solution Toolbox — 35 Cases Indexed by Approach*

本附录把全书引用的真实案例按解决方案重新分类：同类方案处理同类问题，供遇到类似问题时对照查阅。案例池共三十五个——FDE案例集二十四案，加斯坦福手册中成篇写透的十一案；每个案例取其解法，一案多招的在各招所属的类里分别落位。附录编号至H后，I、J两个字母跳过未用，下一附录为K。

用法：先在下表对照自己的问题，定位方案类别，再入类查阅条目。每条按五项展开——背景（企业／业务）、痛点（表现／代价／旧办法）、解法（思路／前置／链路／机制／落地）、效果（量化／人与组织／延伸）、教训与边界（弯路／边界），材料缺的段不设；案例出处标注在条目标题中。一个痛点指向多类的，说明该问题存在多条解法路径，宜分别查阅后再定；第九类（组织与人）贯穿前八类，另设八个参见条。

## 第一类　把散的经验和资料变成可查的库 {#appK-1}

这一类方案针对知识与资料的分散状态：经验存在于个人，文件散落在各处，资料分属多个系统。解法方向一致——先把散的收拢成可查的库，再接入使用场景；差别在于收拢的对象与接入的位置。

### K1.1 带教知识库：跟岗摸问题，攒库进培训（FDE NO.1）

#### 背景

- **企业**：德国斯图加特一家制造零部件的企业，七八十人，多条产线、多种型号产品。
- **业务**：生产知识非常细——不同零部件要调参数、涉及不同金属材料的配比；零部件面向的使用环境不同（耐强酸、耐磨损），材料配比、设备操作和生产经验直接影响质量。新人培养靠师徒带教，一个新人两三个月起步。

#### 痛点

- **表现**：相当一部分生产知识不在标准文档里，掌握在老师傅手里——某个产品该怎么调、什么情况下参数要变、设备出现某种状态怎么处理。这些长期实践形成的隐性经验，很难靠一份操作手册完整记录。
- **代价**：
1. 老师傅生产任务重，没有足够时间持续带教；
2. 经验丰富的员工接近退休，企业最担心的是"人走了，经验跟着人一起走"；
3. 培养周期长，带教持续占用老师傅的时间。
- **旧办法**：人带人。师徒制本身是自然的知识传递方式——老师傅不仅知道标准答案，还知道什么时候不能机械照标准答案执行——过去一直运行良好。撑不住的原因是业务环境变化：师傅没时间、临近退休，而企业想把依赖个人的经验沉淀为组织能长期使用的知识。

#### 解法

- **思路**：把老师傅最有价值的经验先留下来，让过去必须反复问老师傅的问题通过另一种方式完成第一次解答；真正复杂、需要判断的问题回到老师傅——重新分配人在培训流程里的作用。知识库不做独立入口，嵌进原有培训流程。
- **前置**：不靠访谈，先跟岗。一线员工不一定愿意花时间接受访谈，很多工作细节自己也描述不出来；跟着员工走一天流程，看他在哪里停下来、哪里需要问人、哪些问题反复出现。再找主管梳理生产线和培训流程，统计新人最常出现的问题、最容易反复出错的知识、哪些属于老师傅独有的隐性经验，整理成一张知识地图。
- **链路**（入库 → 测试 → 接流程 → 陪跑）：
1. 知识入库：企业已有文档先导入，老师傅隐性经验显式整理，经文档解析、RAG处理成可问答的知识库；
2. 测试验收：前期统计的高频问题直接当测试集——文档解析约95%、问题召回片段准确率80%以上，小范围测试达标才算技术路径跑通；验收标准与客户共同商定，不由技术方单方面定；
3. 接入流程：知识能力接进企业原有培训平台，设计在线课程式打卡——新人规定时间内的学习进度可见，带教师傅可查看，每节课程设问答做简单验收；
4. 上线陪跑：持续调整前端易用性、页面与问答效果，陪跑接近两个月。
- **机制**：AI进入原有培训流程，不要求员工改变工作习惯去适应新工具；客户已有可用的技术栈、平台尽量复用，不为展示技术能力推翻重做。
- **落地**：从立项、调研到陪跑约半年，净投入约四个月；上线后持续修改——员工怎么用、哪里不习惯、老师傅愿不愿看、新人能不能看懂，都反过来要求产品调整。

#### 效果

- **量化**：无百分比数据。
- **人与组织**：老师傅从重复回答所有问题，转向关注新人学习进度与处理复杂问题；高度依赖个人的经验传承，开始变成可沉淀、可检索、可追踪的组织流程。
- **延伸**：企业第一次能比较完整地知道，哪些经验真正不能随老师傅退休而流失；培训进展从依赖带教师傅的个人观察，变为平台上可见、可追踪。

#### 教训与边界

- **弯路**：最初靠访谈了解需求，发现一线员工说不清、隐性习惯问不出来，改为跟岗；以为"文档扔进去、AI能答题"知识库就算建成——实际必须回到前期那批真实问题上验证过才算。
- **边界**：
1. 技术指标（解析率、召回率）没有行业统一标准可套，先小范围测试看当前水平，再与客户共同确定验收线；
2. 系统上线不等于项目结束，真正的落地发生在上线之后。

### K1.2 文件重组：给散资料建关系，库留在企业（FDE NO.11）

#### 背景

- **企业**：外贸礼品公司，十几个人，年销售几个亿，产品含起瓶器这类小商品。
- **业务**：电脑里有样图、美工图、参考图、客户交付图、各种产品模板，分散在不同电脑、不同文件夹。企业负责人的原始需求很具体：能不能直接跟AI说一句"帮我找一下某个客户之前用过的某个模板"，就把东西找出来。此外还有一堆碎需求——看阿里国际站关键词表现、给公司网站持续发文章、产品图自动套进已有海报模板。

#### 痛点

- **表现**：企业的数字资产没有被组织起来——文件都在电脑里，但AI不知道文件之间是什么关系，人自己也未必知道；企业也缺少AI可以直接运行的环境（网络、电脑环境、权限、文件结构、工作流程）。
- **代价**：找一份旧资料靠人翻；碎需求几十上百个，每个都找外包开发，成本承担不起，而且很多问题没清晰到能写成需求文档——企业负责人知道"这里不太顺"，但不知道该开发什么。
- **旧办法**：企业负责人花过约五万元买标准化服务（国际站数据、外贸网站）——产品有一定价值，但遇到个性化问题后没人继续陪跑，也没人告诉他工具怎么和自己公司的工作方式结合。

#### 解法

- **思路**：不急着开发功能，先把现场环境和文件关系理顺；数据留在企业、开发能力送进去；交付目标从"做一个工具"改为"沉淀企业自己解决问题的能力"。
- **前置**：先修基础设施——客户内网四台路由器、两台光猫、一台交换机、一个软路由，串得乱且不稳定；第一天几乎在当网络工程师。内网不通、设备环境不一致，再好的Agent也跑不起来。
- **链路**（修环境 → 重组文件 → 本地开发 → 夜间跑长任务）：
1. 文件重组：重新组织散落各电脑的资料，建立文件之间、文件与客户／产品／项目之间的对应关系——让AI知道哪个文件属于谁；
2. 本地部署：合同、客户资料等核心资产企业负责人不外传，于是把框架、原则、规范和Demo整理成任务包，部署到客户自己的Codex环境，本地跑了约四十小时；
3. 反馈迭代：测试产生的日志、问题、记录由客户侧AI整理回传，据此修改规范和任务，再投回去继续适配；
4. 远程协同：自建远程通道，让AI在后台连接客户电脑上的AI执行任务，长任务放到晚上跑，不占员工白天干活。
- **机制**：数据不出企业，开发与适配照常进行——改变了"驻场工程师必须守在客户电脑旁"的工作方式。
- **落地**：从一个非常小、非常具体的问题开始建立信任——客户拿来一件带一排不规则刻度的三角尺样品，美工和3D打样都没搞清刻度是什么，AI约十分钟查清产品来源、刻度代表角度；当场立信之后，企业负责人很快释放出十几到二十个新需求。

#### 效果

- **量化**：无百分比——项目在第一阶段，交付尚未全部完成。
- **人与组织**：企业负责人对AI的判断从"买一个工具"变成"重新思考公司怎么工作"；问法从"要不要试一下AI"变成"我公司还有哪些问题可以这样解决"。
- **延伸**：对业务快速增长、人力跟不上的企业，企业负责人意识到未来新增业务不一定都要靠增加人力解决——这个认知变化的价值，可能超过单个工具省下的成本。

#### 教训与边界

- **弯路**：安装包发过去报错、改了再发又报错——环境不一致是第一现场问题，进场先把每台电脑的网络、权限、运行环境摸清；按传统做法把数据打包拿回公司开发，走不通，才改成能力送进去、数据留下来。
- **边界**：大量工作并不"AI"——修网络、处理Windows环境、梳理文件命名、解决权限、等企业负责人测试；对企业负责人这类客户，当场解决一个他正为之付出时间的真问题，是建立信任最快的方式，概念讲完就忘。

### K1.3 跨库拉齐：一个报障，五六个库的资料自动凑齐（斯坦福·半导体现场服务）

#### 背景

- **企业**：美国一家企业级固态硬盘制造商；公司内各部门技术成熟度不一——工程和IT在前，运营和财务居中，法务和HR靠后。
- **业务**：企业客户报障后，现场服务工程师要先收集技术资料再做诊断——产品规格、测试库、数据表、工程日志，分别存在五六个不同的库里，各有团队分管。

#### 痛点

- **表现**：一个报障进来，工程师要跨五六个库凑资料——资料不集中、各有其主，全凑到一起才能开工。
- **代价**：光数据收集这一步，服务承诺（SLA）就是四十小时；此前的资料齐全率为0——多数故障在资料不全的状态下处理。
- **旧办法**：各部门自建过基于大模型的分析Agent——演示环境里能跑，进生产不行。问题不在技术：工程部门各建各的，没有共享标准，没人对推广和采纳负责。

#### 解法

- **思路**：组织先行，再上系统——需要跨部门采纳的方案，部门级授权到顶了，必须公司级支持。
- **前置**：三项组织动作——每个部门设一名AI冠军（champion）带动同事采纳；同级压力不够时升级到CEO，把AI采纳写进公司OKR；办AI演示日，CEO到场发奖，传递"这是公司战略、不是IT实验"的信号。
- **链路**（报障 → 自动拉库 → 汇聚开工）：
1. 报障进入：客户问题进系统；
2. 多智能体取数：Agent自动去五六个库，把与该客户、该问题、该工程领域相关的资料拉到一起；
3. 汇聚交付：工程师拿到已凑齐的资料开工诊断。
- **机制**：部门间成熟度不同，靠各部门的AI冠军做同侪带动；法务、HR等非技术部门起初滞后，同侪压力不足时由公司OKR兜底。
- **落地**：原文未展开试点节奏，可确认的是组织动作先于系统建设完成。

#### 效果

- **量化**：数据收集时间从四十小时以上降至一小时以内；资料齐全率从0到95%以上；产品测试周期缩短20%。
- **人与组织**：跨部门采纳的阻力被OKR与演示日的组合打破——标准沟通和培训做不到的事，绑定考核与高层站台做到了。
- **延伸**：案例负责人的总结是"AI是心态转变，完全是变革管理驱动"——这个案例真正的产品是组织机制，不只是多智能体系统。

#### 教训与边界

- **弯路**：第一轮大模型分析Agent演示能跑、生产不行——没有共享标准与采纳责任的分散建设，注定停在演示阶段。
- **边界**：部门级发起的AI项目，一旦需要跨职能采纳就会遇到天花板；把采纳绑定公司OKR与高层认可，才穿透常规沟通与培训穿不透的阻力。

### K1.4 案件工作台：先建案再交互，散材料沉淀成案件库（FDE NO.3）

#### 背景

- **企业**：法律行业，服务对象为律所诉讼律师团队，处理商事合同纠纷、公司股权争议等复杂案件；产品为"法索AI"（原文图注：上线两个月用户已遍布全国多个城市）。
- **业务**：一个典型商事诉讼案件包含合同、聊天记录、财务凭证、证据文件等数十种材料类型，总页数动辄上千页；诉讼周期通常持续数月甚至一年以上，期间新证据、争议点不断出现。

#### 痛点

- **表现**：材料高度非结构化，仅整理就可能耗费3到5个工作日；涉及十几个当事人的案件，光梳理人物关系就需要两三天。当事人原始描述是日常口语，要提炼为具有法律意义的要件事实再匹配请求权基础，新人和资深律师的效率差距可达3到5倍。律师每次重新进入案件，都要花大量时间恢复记忆、回顾之前的分析脉络。
- **代价**：律师每天大量时间消耗在案头工作上——既是决策者，也是被案头工作困住的执行者；产能瓶颈不在专业判断，而在信息处理的效率。
- **旧办法**：法律数据库（北大法宝、威科先行）查法条判例，文档管理系统归档，早期法律问答工具生成简单文本。这些工具只解决"查"和"生成"两个单点动作，一次性查询的设计与律师反复回到同一案件补充分析的工作节奏脱节；律师要在五六个系统之间切换、案件上下文被割裂，过去十年律所引入的数字化工具落地效果普遍不理想，大部分沦为查法条的辅助手段。

#### 解法

- **思路**：不改变律师原有工作方式，在原流程中找AI嵌入位置；大模型管理解，专业系统管知识图谱与精确检索，律师管最终判断与专业责任。
- **前置**：进律所现场——从早上九点律师打开电脑开始，观察其如何接收客户邮件、翻阅纸质案卷、在多个系统间切换查找信息；旁听案件讨论会，追问案件从头到尾的步骤、每步交付物、给谁看、什么结果才真正可用；与合伙人高频访谈，弄清他们想在哪里省时间、哪些地方即使省了时间也不放心，以此决定哪些留给人决策、哪些让AI直接干好交付。
- **链路**（拆流程 → 定分工 → 先建案再交互 → 经验入库）：
1. 拆解案件流程：在原流程中寻找AI嵌入位置——辅助通读上千页材料整理案件概要、辅助把口语描述转换为法律语言再检索、辅助梳理证据关系／人物关系／法律关系，最终形成7个标准模块，让重复但高价值的工作自动化跑起来；
2. 大模型与专业系统分工：大模型负责自然语言理解、文本摘要和初步法律推理，专业系统负责案件知识图谱管理、法律条文结构化检索和判例精确匹配，确保法律引用准确性和可追溯性，两者通过统一的案件工作空间整合；
3. 案件工作台：产品入口从聊天窗口改为工作台，原则是"让用户先建案，再交互"——律师先上传案件材料，系统自动构建案件知识图谱，AI在完整理解案件上下文的基础上再交互；所有分析结果、策略建议、文书草稿沉淀在案件空间，形成可追溯的工作记录；
4. 隐性经验入库：与优秀律师一起工作，拆解其做判断时的决策逻辑，把请求权基础分析的三层四步法、证据链构建的逻辑规则等思维框架，转化为系统可以执行的流程节点。
- **机制**：AI负责信息处理、分析整理和重复性工作，专业系统承载案件上下文和知识流程，律师负责最终判断、策略选择和专业责任；律师不需要学习提示词工程，用专业语言表达需求即可；AI生成的必须是律师能直接使用、能交付给客户／法院／其他专业人员的结果。
- **落地**：第一次使用时就引导先上传材料，让AI当场展示理解案件背景之后的价值——自动生成案件概要、自动梳理人物关系图；让用户亲眼看到价值，比任何解释都有效。

#### 效果

- **量化**：一个涉及14个被告的案件，过去一个被告对应的请求权基础分析需要2到3小时、全部整理完成需要2到3天，AI辅助下律师把案件材料交给系统，一个晚上完成；一位律师距开庭只有3天、案件材料超过100万字，一天内完成案件整体梳理并制定开庭策略，材料整理效率相比纯人工提升约70%。
- **人与组织**：律师角色从执行者向决策者转移，精力投向与客户沟通、判断案件方向、制定策略；入口改为案件工作台后使用门槛明显降低，律师更快接受了AI的介入。
- **延伸**：专业能力变得可复制——过去优秀律师的个人经验很难复制给团队、不同律师经验差异导致交付质量不稳定，现在专业方法可被工程化沉淀，更多律师获得稳定的辅助能力；AI从一次性工具变成持续陪伴案件全过程的协作系统。

#### 教训与边界

- **弯路**：最初把入口设计成智能对话框——律师每次提问前都要向AI重新描述案件背景，一个案件信息量巨大、不可能每次对话完整复述，对话式交互实际增加了负担；案件更像长期项目，要持续承载大量材料、过程记录和变化中的信息，一次对话根本装不下。
- **边界**：
1. 隐性经验的结构化是第一挑战——难点超越知识本身，在律师如何思考：什么事实需要关注、如何把普通人的描述转成法律语言、不同证据如何形成逻辑关系，需投入大量时间与优秀律师一起拆解；
2. 从业务问题出发、用业务语言定义需求——若一开始从模型能力出发，可能只会做出法律知识问答工具；不了解一个行业时，没有资格替行业定义问题。

### K1.5 物料检索：先清洗数据，再上语义检索（FDE NO.8）

#### 背景

- **企业**：海外工业企业，小到一副手套、一颗螺丝钉、一副耳塞，大到一辆卡车、一个机械臂都要进ERP数据库；与这套数据库发生交互的团队大概15个，案例涉及十几个部门。
- **业务**：ERP承载企业长期的库存管理流程，录入、采购、合同、仓储各环节职责明确，各团队围绕它运转。

#### 痛点

- **表现**：几乎所有部门都在抱怨ERP不好用，最典型的是数据不干净和搜索能力弱——一套较老的工业软件靠传统字段和关键词检索，与电商式搜索体验差距大。业务人员"明明知道这个部件数据库里有，上次还用过，但现在就是找不到"，找不到就重新录入，重复数据越积越多、数据越脏越难找到正确物料，最后买错、买重或搞错单位；同一物料还可能存在不同名称、描述方式、单位或录入习惯。
- **代价**：
1. 工业采购牵扯真金白银——买错的东西往往不退回去，只能再买一个正确的；
2. 错误采购的东西留在仓库一放可能就是几年，清理库存时按规则处理掉——企业真正损失的钱藏在这里；
3. 问题不显性，没有人把历史记录找出来、分析这些错误每年造成多少损失。
- **旧办法**：业务人员靠经验兜底——知道编码按编码找、知道名称按名称找，实在找不到就按原流程重新录入。历史数据越积越多，关键词检索和字段匹配处理不了，经验兜底越来越吃力；先顶不住的是那套搜索系统——数字化这一步企业早就迈出去了，工具本身成了新瓶颈，继续要求员工录入更规范、搜索更仔细，很难从根本上解决。

#### 解法

- **思路**：AI只做该做的部分——先把历史数据洗干净，再上语义检索；最终是不是采购、采购多少，由业务人员拍板。
- **前置**：不带现成产品进场，先对整个客户做长时间业务摸排，进入案例后又围绕ERP及其上下游团队持续数月深入访谈，有时直接坐在业务人员旁边看他实际怎么工作——很多问题只在会议室里问问不出来；访谈后继续研究拆解、做根因诊断，梳理出大约15个可进一步处理的功能点。
- **链路**（追根因 → 定优先级 → 清数据 → 语义检索 → 基线验证）：
1. 追到根因：把"ERP不好用"放回完整业务链条——搜索困难→重复录入→数据污染→错误／重复采购→库存积压→最终报废→真实财务损失；这条链路成立，才知道这个AI应用到底值多少钱；
2. 定优先级：功能点整理成列表，召集十几个部门的负责人和代表逐项确认、参与投票；FDE内部再从七八个维度评估每个用例——数据能不能拿到、处理结果能不能写回业务系统、AI能不能解决、业务人员愿不愿意采用等；
3. 数据清洗与标准化：检索之前先把历史数据里的重复和不一致处理掉，让语义检索有干净的底子；
4. 语义检索：理解业务人员"我要找的东西"背后的语义，把同一物料的不同叫法对上号，从源头减少重复录入，进一步减少错误采购和重复采购；
5. 基线验证：从历史数据建立基线，小规模实验逐步扩大——AI有没有减少重复数据、错误采购有没有下降、对应的采购浪费有没有被避免。
- **机制**：价值不由FDE自己宣布——需经严格的计算方式得出，且要客户业务人员确认，只有客户说出"对，这笔钱确实是因为这个应用被节省下来了"，价值才真正成立；FDE持续验证"问题、方案、业务价值"三者的关系，让每一步建立在前一步的验证结果上。
- **落地**：从容易见效的场景开始，最好几个星期、甚至两周左右就让业务部门看到初步结果，信心建立起来后才愿意主动参加后续行动；允许中途反复——问题定义不对就回到问题发现，范围铺得太大就重新缩小；上线后移交业务部门，继续跟进效果还在不在。

#### 效果

- **量化**：无可报数字（原文未提具体量化数字）。可报口径：最终看的是客户是不是少买错东西、少重复购买了——模型准确率、搜索速度都只是过程指标，真正的业务结果是采购行为有没有改变。
- **人与组织**：把过去不可见的问题变成可以计算的问题——此前客户知道错误采购和库存浪费存在，但没人分析过这些错误每年造成多少损失；业务部门参与功能点投票与优先级确认，"大家都知道有问题，但没人知道问题值多少钱"变成可发现、可干预、可持续衡量的经营问题。
- **延伸**：最终落地的是数据清洗和语义检索——搜索只是手段，让业务人员更容易找到已经存在的物料；可复用的方法论（问题发现、根因分析、用例判断、ROI定义、小规模实验、和业务部门一起验证、持续衡量）比某一个具体的AI功能更值得沉淀。

#### 教训与边界

- **弯路**：花数月去理解一个看起来和AI没有太大关系的ERP业务流程，对很多工程师是最难接受的部分——不做这些脏活累活，后面的AI很可能只是在错误的问题上做得更漂亮；技术能做、落地却难——数据拿不出来、老ERP不让把处理结果写回去、业务部门不许碰现有系统、业务人员不相信AI结果，任何一个解决不了，用例都可能失败。
- **边界**：
1. 不要拿着AI去找问题——手里有Agent、RAG、工作流产品就去问客户"哪里能用"，很容易变成拿着锤子找钉子；"ERP不好用"不是一个问题定义，要一路追到真实的财务损失；
2. 把ROI定义放在项目开始——很多AI项目上线之后才开始问创造了多少价值，往往已经晚了；
3. FDE不能是"东西做完、钱到账、人撤走"——业务部门最终不用，或三个月之后效果消失，这个应用就不能算真正落地。

### K1.6 知识萃取：先把经验拆成流程入库，再做Agent（FDE NO.14）

#### 背景

- **企业**：省属国企一级子公司，业务覆盖服装、美妆、3C等十多个电商业务线；数字化建设比较扎实，有OA、ERP、数据中台，有自己的信息化部门；法务团队只有两个人。
- **业务**：多条电商业务线运转，法务两人要面对不同业务线、不同合作伙伴的大量合同；管理层在GPT等大模型出现后提出模糊要求——"数字化建设在国企中已经领先，能不能再往AI走一步"。

#### 痛点

- **表现**：大量企业知识没被沉淀结构化——法务审核过很多合同，只留下修改后的合同，为什么修改、哪些条款关键、哪些不能省都在法务脑子里；客服知识体系在员工脑子里，没进入AI可使用的数据系统；员工执行复杂流程多年后觉得步骤"理所当然"，意识不到自己在执行流程。
- **代价**：
1. 业务要扩张、团队能力难同步扩张——国企有编制限制，人员不能跟着业务无限增加，懂电商懂业务的人才不一定愿意进国企；
2. 专业岗位承接不了越来越多的工作，又不能简单靠增加人手解决，懂业务的外部律师也不好找；
3. 通用大模型本质是概率生成——对A公司流程理解正确不代表对B公司正确，流程不被明确梳理出来，模型就只能自己"生成"。
- **旧办法**：传统软件交付——技术团队按客户实际做配置、开发定制，复杂的先做咨询梳理流程再交付系统。跑得通的前提是被信息化覆盖的业务能被讲清楚、流程相对固定；业务规模变大、流程越来越复杂后，靠人、靠经验、靠传统软件定制的方式越来越难扩张。

#### 解法

- **思路**：先把流程和知识从人脑子里萃取出来建库，再做Agent——流程必须来自企业自己；AI定位为员工助手而非替代，最终由人确认、签字、承担责任。
- **前置**：逐个场景判断值不值得做——技术上目前做不好的不硬做，技术能做但实际价值太低的也没必要做，帮团队避免很多"做出来没人用"的玩具。
- **链路**（萃取 → 入库拆流程 → 全员培训 → 助手进流程）：
1. 知识萃取：引入"知识萃取师"角色——与有行业案例和成熟模板的传统咨询不同，这个角色要把客户自己脑子里的知识和经验真正萃取出来；要求业务人员把原来的工作过程讲出来：到底怎么做、为什么这么做、哪些情况例外、什么情况下必须人工判断，本质是给AI准备"业务世界"；
2. 知识入库：把散落在文档和人员经验里的内容沉淀下来，把一个岗位原来依赖经验完成的工作拆成明确流程——先梳理流程，再做Agent；
3. 全员培训：业务骨干连提示词是什么都不知道、不知道知识萃取该提供什么，与其项目组逐个教，不如直接做AI通识培训；
4. 助手进流程：AI负责大量重复工作，真正进入工作流的Agent大部分最终需要人确认——法务场景中，AI根据历史合同和业务信息识别关键条款、发现风险，先做一轮筛查把需要重点关注的内容挑出来，交给法务最终确认。
- **机制**：项目按"IT部门牵头的技术项目＋人事部门牵头的组织转型项目"双线定位；法务、财务等涉及责任的问题AI最终不能承担；业务人员不愿把知识变成组织资产时，把AI从"替代"切换到"助手"，同时让人事制度、激励机制跟上——员工为什么愿意参与、AI完成重复工作后员工做什么、有没有业务增长、晋升路径、新激励。
- **落地**：第一年IT部门牵头搭出技术底座，遇到瓶颈后改由人事部门牵头、从培训开始重新推进；全员培训后，负责行政物品的同事自己发现需求，通过AI平台、基于数据中台的MCP能力、用提示词做了一个补货Agent——员工在IM上问机器人"我今天要领两节电池，还有没有"，系统查库存，库存不足提醒行政人员补货，补货完成后发信息给需要电池的员工。

#### 效果

- **量化**：法务场景——客户原本至少还要招一个法务，因为有了AI法务助手，这个招聘的编制节省了下来，目前两个法务工作状态也比较正常；如果一定要用人数折算，就是一人年的综合成本。
- **人与组织**：不懂技术的行政人员自己用提示词做出了补货Agent——在企业内部培养出了新的AI使用者、新的FDE，原文称这可能比外部团队替他做一个Agent更重要；员工开始主动发现问题、主动拆流程、主动用AI解决问题，FDE从"交付工具"转变到"改变组织能力"。
- **延伸**：企业开始尝试建立自己的企业AI成熟度模型——从流程能不能被萃取、数字化程度怎么样、AI到底能实现到什么程度等维度，判断场景适不适合做AI。

#### 教训与边界

- **弯路**：最初按传统思路以技术人员为主搭技术底座——知识库、模型能力、Agent接进客户已有信息化系统，技术上做出了东西，但客户员工没有用起来、业务没有真的变化；以为董事长要求业务骨干配合、找几个人就可以开始，结果员工连提示词是什么都不知道；第一年IT部门牵头遇到瓶颈——问题重心从"系统怎么做"转到"员工怎么用""流程怎么改""组织怎么配合"。
- **边界**：
1. 踩过最大的坑不在技术，难度排序是：人最难，其次组织，再是数据，最后才是技术；
2. 业务人员觉得AI最终要替代自己时，自然不会主动交出经验和流程；
3. 数据没有想象中完整——数字化基础很不错的企业仍有大量业务没有结构化沉淀，不能因为客户有ERP、有数据中台就默认它做好了AI准备；
4. 中大型企业的AI落地一定是一号位工程，企业负责人只扔给IT部门大概率面临失败。

## 第二类　机器做第一遍：单据核对与条目分拣 {#appK-2}

这一类方案针对单据、材料、告警的人工核对与分拣：图片一张张点开看，两边的数一项项对，告警一条条判。解法方向一致——让机器做第一遍，人只判机器拿不准的和真差异；差别在于材料有多脏、流程串到哪一步。

### K2.1 审单自动化：材料逐类训练，串回原流程（FDE NO.2）

#### 背景

- **企业**：浙江一家车管所。当地政务网办数字化程度高，群众线上提交业务、上传材料（身份证、营业执照、合同、发票等，基本都是图片，拍摄质量五花八门）。业务链上还有驻点快递企业——车管所审核制证后，由快递负责打包寄递，快递企业投入人员驻点。
- **业务**：网办流程为群众在线提交，工作人员后台审核——点开图片、肉眼判断材料对不对、信息全不全，再录入系统办理。

#### 痛点

- **表现**：前台数字化了，后台仍靠人工——工作人员一张张点开图片看，核对后再录入。
- **代价**：
1. 慢：单件业务从头到尾约十五分钟；
2. 累：高度重复，长时间盯屏看照片，有工作人员反馈"眼睛都受不了"；
3. 量上不去：日办件七八百，卡住的不只是群众服务——审核效率决定办件能力，也影响驻点快递的经营成本和服务模式能否持续。
- **旧办法**：没有特别解法，就是靠人。流程运行已久、大家习惯，甚至不被认为是个需要解决的问题；业务部门的第一反应是"现在这样不也能干吗"。真正的变化来自业务条件——经济环境变化、驻点企业经营压力增大，希望减人又增量，"不够痛"的效率问题才变现实。

#### 解法

- **思路**：让机器替代人工完成重复性的"看、读、填、搬"；AI嵌回原业务流程，不做孤立工具；先用结果建立信任，再推动正式立项。
- **前置**：入口是一个遗留系统运维小项目——原承建商倒闭、源码不完整、多种技术栈混杂，很多公司不愿接。驻场运维期间观察出真需求，没有一上来就讲"上AI"。
- **链路**（拆活 → 逐类训练 → 串流程 → 异常转人工）：
1. 拆解人工活：整个审核拆成看图片、识别材料类型、读取关键信息、判断是否符合要求、填写数据、系统间搬运——"看"交给机器视觉与OCR，合同等复杂文本的信息提取逐步引入大模型，重复填写与流转交给RPA；
2. 逐类磨识别：九类图像材料（合同、发票、营业执照、身份证复印件等）逐类收集真实素材、标注、训练。真实材料极不标准——只拍到国徽的身份证、各家金融机构格式各异的小字合同、复印后再拍照的低质图片——异常样本不断滚回训练；识别率从70%多磨到98%左右，前后约半年；
3. 串进原流程：识别、审核、填单与后续系统流转串成一条线，通过RPA接进原有Web系统与公安部统一业务系统——大部分正常业务自动完成，工作人员看结果和报表，异常才人工核验；
4. 先做后立：前期承担售前成本，先做部分场景，用真实效果替代PPT说服；叠加人员与业务量压力后，项目才正式立项。
- **机制**：AI成为原业务流程的执行环节，旁边不多出一个独立工具；工作人员不需要重新学一套工作方式。
- **落地**：以运维小项目进场，观察、验证、建立信任、立项、迭代，研发迭代周期约半年；验收后又接到新业务，双方共建AI创新实验室。

#### 效果

- **量化**：单件全流程审核十五分钟缩至三五分钟；日办件从约七八百提高到1100左右——AI没有凭空创造需求，很多群众本来就有办理需求，只是过去卡在审核产能上；驻点人员不增，办件量保持并略增。
- **人与组织**：工作人员从打开图片、检查材料、填写信息的重复劳动中释放，时间转到群众咨询、新增业务等需要判断与沟通的事情上。
- **延伸**：项目成功的标志是验收之后，客户还愿意继续做第二个、第三个项目——后续双方共同成立了AI创新实验室。

#### 教训与边界

- **弯路**：无明显技术弯路，但识别率是磨出来的，不是一次到位。
- **边界**：
1. 材料数据极不标准：识别率从70%起步，靠真实样本滚了半年才到98%，别按开箱即用排计划；
2. AI把人工审核里的"放宽"暴露出来：过去人工审核存在一定放宽尺度，自动审核跑起来后，"识别出来以后怎么办"成了业务决策问题——完全按技术标准执行可能影响业务量和合作关系，保持宽松又失去自动审核的意义。做法是把问题和数据客观呈现给甲方（不同审核尺度下每天能处理多少、业务量怎么变），由业务负责人定夺；
3. 组织协同比算法难：落地涉及不同部门、不同角色、外部合作方，流程改变会影响一些人的原有工作和利益——要会沟通、协调、项目管理，甚至算利益账。

### K2.2 对账第一轮：机器全量核，人看差异（FDE NO.10）

#### 背景

- **企业**：以线下零售为主的消费品企业，年营收几十亿元，门店主要开在百货公司和商业综合体。
- **业务**：资金结算链路特殊——门店收银系统一套数据，商场一套结算数据，资金经商场结算给企业；每个结算周期都要把两边的数据和单据重新核对一遍。

#### 痛点

- **表现**：店员或店长拿着纸质单据或其扫描件，从不同系统拉出数据逐项核对；发现对不上要双方重新核对，改完可能又出新差异，来回拉扯。
- **代价**：
1. 业务层：对账不彻底，意味着本该收回的钱可能被遗漏；
2. 流程层：承担对账的店员店长同时背着销售指标，对账挤占经营时间；
3. 信息层：两边数据没有天然打通，纸质单据又增加人工成本；一个周期一两个人天。
- **旧办法**：拉多系统数据、看总额、看分项、针对差异找原因——单店或少店时人完全做得来。规模扩大后边际成本越来越高；人工除慢之外还产生连续返工，员工觉得某些差异不值得追就放弃；总部给门店设"容忍区间"，小区异差异直接不追。

#### 解法

- **思路**：不整体AI化，先接管最标准、最重复的第一轮核对，把人从机械比对中释放出来；多个候选需求里挑正反馈最快的先做。
- **前置**：需求排序——客户当时还有自动化客服、竞品对比等候选；客服要长数据周期才能证明商机增量，竞品分析的结果短时间难验证；对账省多少人工、追回多少钱，直接可算。
- **链路**（识别 → 比对 → 分流 → 人工判断）：
1. 第一轮核对：OCR加视觉，对纸质／图像单据与相关信息识别、比对；
2. 定时运行：自动化工作流按结算周期定时执行；
3. 结果分流：已能确认的结果先筛出，人只处理真正需要判断的部分。
- **机制**：第一天就分两阶段设计——第一阶段尽量轻量，Cherry Studio加一台本地电脑即可运行；第二阶段扩展到几百上千家门店时，再加后端数据能力与冗余机制。轻量起步不等于没有扩展规划。
- **落地**：先落上海几家门店（个位数）验证价值；不给一线增加动作——AI出现在原有流程里，员工拿到的是第一轮已处理的结果，不需要维护自己的系统。

#### 效果

- **量化**：一个周期从一两个人天压到几小时。
- **人与组织**：员工把它理解为"有人帮我做完第一轮对账，我只看结果和处理真差异"，接受度高；店员时间回归销售与门店经营。
- **延伸**：AI把人工流程掩盖的问题暴露出来——门店差异少的百分之一二、多的两三个点，有少收有多收，最终看净差；对线下零售企业，落到纯利层面不是小数。核对成本降下来后，过去因成本太高而放弃追的那部分价值，被重新捡回。

#### 教训与边界

- **弯路**：此前做电商横向比价，判断"AI应该能解决其中七八成"，现实复杂得多——平台风控与反风控持续博弈，找到的方案很快被堵，交付周期拉长、可覆盖场景越缩越小。
- **边界**：一个领域如果已经有公司专门靠它生存，先认真研究——它解决了什么难点、掌握哪些信息差、为什么值得长期投入——再判断自己进不进。

### K2.3 票据入账：先砍模板，再上AI（斯坦福·物流发票）

#### 背景

- **企业**：美国一家十亿美元级物流公司，管理大批冷藏挂车车队；全国供应商（修理厂）为挂车做维修——换轮胎到换传感器。
- **业务**：每年从全国各地收到十万张以上发票，渠道五花八门——邮件、传真、电话报修转述（"很多修理厂在偏远地方，直接打电话说修了什么"）。七名全职员工专门从事此事：合并发票、对内部模板、验证工作、录入ERP、生成客户账单。

#### 痛点

- **表现**：发票量与形态的多样性造成持续的运营负担；多年积累的发票模板冗余且不一致——750套模板大量重复，从来没人审查过。
- **代价**：七名全职人力全部投入在对票与录入上；积压随业务增长持续恶化。
- **旧办法**：纯人工处理各渠道发票、对模板、录系统——流程能跑，但人力成本与积压随业务增长不断上升。

#### 解法

- **思路**：先简化流程，再上AI——流程不清干净，AI无法工作；建一套系统，自动读取任意渠道进来的发票、理解内容、直写财务系统，取消人工处理环节。
- **前置**：流程简化——750套历史模板精简到几百套（多数重复、无人审查）；这是AI动工前的必做步骤。
- **链路**（多渠道归集 → OCR解析 → 语义映射 → 直写ERP）：
1. 渠道归集：邮件、传真、电话转写等多渠道发票统一进入系统；
2. 解析抽取：Azure Document Intelligence做OCR解析；
3. 语义映射：Azure OpenAI把发票内容映射到精简后的模板分类；
4. 直写系统：验证过的数据直接写入MS Dynamics D365，不再人工录入。
- **机制**：业务专家（SME）在日常活之上逐张校验AI产出的发票，解释每一个错误帮模型改进；总裁每周过问进度、当场拆瓶颈——"总裁每周check in，然后团队其他人才跟上来"；两名初级IT从第一天嵌入，每日站会、按周按月复盘——系统交付时公司能独立运维，不留黑箱。
- **落地**：八周投产。

#### 效果

- **量化**：七名全职降至两名；准确率85%；处理时间24小时以内；创造价值超一百万美元。
- **人与组织**：释放出的人员转到其他瓶颈岗位；运营团队因总裁的每周参与而跟进。
- **延伸**：总裁对精度的态度值得记录——"80%对我们就是完美的。你可以继续优化到95%，但我们不在乎，我们在乎的是立刻省成本、消掉积压。"

#### 教训与边界

- **弯路**：模板问题先于AI暴露——"我们很快意识到这750套模板没有意义，大多数是重复的，从没人审查过"；不清完，AI没法干活。
- **边界**：精度目标由业务定，不由模型定——客户要的是消积压、省成本，不是模型分数；"先简化流程"发生在AI之前，乱流程指望AI直接救，救不了。

### K2.4 报销入单：AI组织信息做判断，RPA填单提交（FDE NO.9）

#### 背景

- **企业**：科研型央企，服务的企业里有大量科研人员、甚至博士；央国企财务工作有大量规则和流程。
- **业务**：以员工报销为例——财务人员先判断费用性质（差旅费、招待费还是其他费用）、该记到哪个项目下，再找出这个人的出差申请、审批记录、所属部门，信息分散在不同的业务流程里；判断完还要打开集团网站、创建单据、一行一行填写提交。付款对象除员工外，还有供应商，以及保证金等各种对外财务流转。

#### 痛点

- **表现**：很多业务超过了"把一张发票录进去就结束"的范围，真正耗时间的是填表之前那段判断过程；业务量上来后，财务人员大量时间花在重复判断和录入上。科研型央企又多一层——科研人员真正该投入的是科研工作，大量时间却被消耗在一个报销流程里。
- **代价**：价值错配——让高价值的人去做低价值、重复性的流程工作，本身就是一种浪费。
- **旧办法**：靠财务人员的专业经验和成熟业务规则，判断和执行前后都要人。撑不住在于无法线性扩张：业务量增加一倍，就要增加一倍的财务人员，这条路很难走得通。

#### 解法

- **思路**：AI主动把分散的信息组织起来辅助判断，多个AI角色互相监督兜底，RPA负责执行；人从处理所有事情，转为只处理真正需要关注的风险和异常。
- **前置**：进业务现场陪跑——业务人员做了十几年，很多判断已成下意识动作，讲不出来；跟着他一起做，看每天怎么处理一笔业务，把流程一点一点拆开。
- **链路**（收票 → 关联 → 判断 → 监督分流 → RPA执行）：
1. 收票：员工在钉钉里告诉机器人"我要报销"，把发票发过去；
2. 关联：AI识别发票，拉出这个人之前有没有出差申请、审批意见是什么、属于哪个部门、对应哪个项目；
3. 判断：AI结合财务规则判断这笔费用归什么科目、哪个项目、按什么规则处理——以前是人自己去系统里找信息、判断信息，现在由AI把信息组织好再辅助判断；
4. 监督分流：财务属严肃业务，不能简单理解成"AI说什么就是什么"——几个AI角色一起工作，一个执行判断、一个监督、一个发现风险；比较确定的业务直接往后走，几个模型判断后仍存在不确定性的进入风险监控，由相关人员重点关注；
5. 执行：RPA自动打开浏览器、进入集团对应网站、创建单据、把相关信息填写进去并提交。
- **机制**：AI处理大部分确定性工作，人只处理风险和异常；按场景选模型——财务场景需要严谨，有些场景用阿里云的模型，有些用其他厂商的模型，还有央国企场景采用本地私有化部署，先确定业务需要什么，再去组合背后的能力。
- **落地**：先做"破冰项目"——找离业务最近、最痛、最容易产生ROI的场景，业务团队自己尝到红利后，才愿意一起做更大的事。数据安全上，敏感财务数据采用数据不出域的私有化部署，曾帮企业采购大型AI算力一体机，投入达两百多万元的量级；顺序是先用小场景证明价值、再推动基础设施建设，不能反过来。

#### 效果

- **量化**：过去处理这些财务场景，工作人员可能需要半个月，甚至一个月；现在通过AI加RPA把一个完整流程跑下来，大概一天、两天就可以完成；项目最终落地10个AI相关应用场景，把财务不同环节逐步覆盖进去。
- **人与组织**：人的操作压缩到非常短的一步——科研人员只需在钉钉里把发票给机器人，信息关联、规则判断、系统录入都隐藏到后台；业务部门从"你要让我用"变成"我希望你帮我继续做"；一套依赖大量人工经验和重复操作的流程，逐步变成可以持续运行的业务能力。
- **延伸**：破冰项目让业务部门拿到结果、甚至成为集团内部标杆后，后面的资源、预算和组织支持更容易获得；条件允许时把AI改造和业务部门的KPI、OKR结合起来，让业务部门自己有动力把项目推下去。

#### 教训与边界

- **弯路**：AI项目组自己设计一个东西、再让业务部门过来使用，业务人员第一反应很可能是"你为什么又给我增加了一个负担"；第一次合作不能大刀阔斧改流程，"原来的流程全部不要、重新设计一套"大概率遇阻；一上来就让甲方先花两三百万元买一台机器，对方很可能会问"我还没看到AI能给我带来什么价值"。
- **边界**：
1. 数据安全红线：敏感财务数据不可能丢到公共模型里处理，必须私有化、数据不出域，并从算力、模型部署、数据环境等底层基础设施解决；
2. 破冰项目三条件：业务真的痛、实现相对可控、ROI能够快速被看见。

### K2.5 包装预审：确定项机器查，判断项留给人（FDE NO.19）

#### 背景

- **企业**：消费品产品生命周期的AI应用，落地在消费品牌和上游工厂、下游渠道；一个消费品企业一年可能要做100多个SKU。
- **业务**：包装审核至少涉及四种视角——设计师检查错别字等基础问题，法律法规人员检查食品法广告法等硬性要求，渠道检查自己的规范（如渠道Logo和品牌Logo的大小关系），产品经理判断包装有没有正确表达产品本身。

#### 痛点

- **表现**：SKU增加后，待审核包装不断堆积、排队等审核，原本所有东西都堆给审核人员。
- **代价**：审核依赖的上下文靠人记——渠道的反馈、历史驳回的经验留在个人脑子里，同类问题换个包装就要从零再判。
- **旧办法**：购买不同的SaaS分别服务研发、生产、渠道等单点环节——过去有效，至少解决了"信息有没有记录"，但系统记录的是结果、信息靠人输入，审核要用的非结构化上下文表单装不下。

#### 解法

- **思路**：把审核拆成"可以自动化"和"需要决策"两类——确定性问题提前自动检查，历史经验持续沉淀，复杂判断留给人。
- **前置**：先定位问题再定义AI。把一个Agent放进业务群，它待了两三周，持续收集业务上下文、不急着解决问题，最后从真实业务沟通中定位到包装审核这个高频问题；再借用HRBP的思路给AI写"岗位说明书"——把真正做审核的人找出来，让业务人员自己拆解平时审什么、输入输出是什么、什么规则可以直接执行、什么情况需要判断。
- **链路**（提交预检 → 分模块识别 → 分层处理 → 经验回流）：
1. 提交预检：设计稿一提交，Skill按规则跑一轮预检，把合规问题、NRV计算、数字矛盾在设计师交给下游之前拦下来；
2. 分模块识别：包装图有密集文字段落、NRV能量计算表格、艺术字变体设计，单靠模型的视觉理解不够——把包装拆成不同的视觉模块，分别选更合适的OCR和VLM方案；固定规则脚本化，热量表和NRV的计算逻辑固化成确定性代码，模型只做解释和补录建议，"蛋白质2.9g、每份40g、NRV5%对不对"这类问题从此可复现地验证；
3. 分层处理：错别字、一些法规标准、能量计算等确定性问题自动检查；渠道要求最初可能需要人工判断，但每一次渠道反馈都被记录，下一次遇到类似包装不需要从零开始；产品经理判断包装有没有把产品表达清楚，留给人；
4. 经验回流：每个模块的审核结果都带来源置信度，每个结论能追溯到原始数据，人接手时清楚该信什么、该查什么；每个最终上线、被市场或监管验证过的包装都是高质量样本，把标准、驳回记录、整改闭环放进上下文——某个渠道的标识位置历史上被退过三次，下次就能提前告诉设计师。
- **机制**：审核从"看一张图、挑一堆错"变成常态化的自动预审——接进产品生命周期管理的基础设施和上下文，上游是产品需求和包装设计，下游是包材采购和物料生产。
- **落地**：原文未展开试点与推广节奏。

#### 效果

- **量化**：无可报数字。
- **人与组织**：法律法规人员减少处理低级错误和返工的时间，产品经理把更多时间放到"这个包装到底应该怎么表达产品"的判断上；每一次渠道反馈、每一次审核经验沉淀下来，个人经验开始变成组织经验，业务人员自己成为Builder。
- **延伸**：效果分三层看——降本增效、提高决策质量、把个人Know-how变成组织能力；渠道产品上线后的销售表现，可反向指导对包装的迭代。

#### 教训与边界

- **弯路**：带着已验证过的方案去客户现场，变成外部人指导内部人；外部人一直待在业务群里，业务同学有压力，改为Agent入群观察；完全由外部的人定义包装审核Skill，容易"外行指导内行"。
- **边界**：能交给AI解决的问题未必都值得做——适合落地的问题至少同时满足：业务同学真实存在的问题、有业务价值、解决之后最好能找到可以衡量的指标，几个条件同时成立非常难；也不能期待AI稳定地100%满足一个没有边界的需求。

### K2.6 采购申请分拣：脏数据起步，足够好就跑（斯坦福·建筑采购）

#### 背景

- **企业**：大型建筑服务公司；现场技术员需要把零部件送到工地。
- **业务**：技术员用纸质表单、邮件和Excel电子表格提交采购申请；一个团队手工把这些录入采购系统，并与零件目录逐条匹配。

#### 痛点

- **表现**：录入与匹配全靠一个团队手工完成。
- **代价**：慢、易错、贵（原文以这三个词定调）。
- **旧办法**：人工录入加人工匹配目录。撑不住之外还有数据底座问题——两侧数据都脏：从非结构化来源的抽取质量不好，OCR给不出好结果；要匹配的结构化数据质量也不一致，核心数据本身质量就不行。

#### 解法

- **思路**：不等数据洗净再动工——按"足够好"设计，流水线每一段吃的是上一段的不完美输出也能增值，例外留给人。
- **前置**：把验收口径从"规定动作"校准为"足够好"——对业务方的说法从"这是你的需求、它就会这么干"改为问"'足够好'长什么样"；接受脏数据起步。
- **链路**（抽取 → 清洗 → 挂目录 → 人审例外 → 建单）：
1. 抽取：AI从纸单、邮件、Excel等非结构化来源抽取采购申请，OCR失效处改用Python抽取；
2. 清洗：用生成式AI清洗——以vectorization与embedding消除杂散字符；
3. 挂目录：对不完美的参照数据做模糊匹配（fuzzy match）挂上零件目录；目录里没有的物料识别出来，并给出替代品建议；
4. 人审例外：例外走human-in-loop，不要求100%准确率；
5. 建单：自动创建请购单（requisitions）。
- **机制**：持续监控、持续喂更好的数据，AI会随之变好；例外环节保留人工，而非追求全自动。
- **落地**：原文未展开试点与推广节奏。

#### 效果

- **量化**：投资额50万至100万美元；生产力增益30%（3至5年预测口径）；预期ROI 3年10倍。
- **人与组织**：例外环节保留人工；原文未提团队编制变化。

#### 教训与边界

- **弯路**：OCR先行受挫——非结构化抽取质量不佳，退回用Python抽取兜底；项目要求从"规定动作"校准为"足够好"标准。
- **边界**：按"足够好"设计而非完美——前提是接受脏数据起步、持续监控并喂更好的数据、不设100%准确率的硬门槛。

### K2.7 告警分诊：机器分类、误报过滤，分析师只接真警（斯坦福·安全运营）

#### 背景

- **企业**：科技服务公司的安全运营中心（SOC），六人团队，中型市场规模。
- **业务**：每月处理约1500条安全告警——分诊、分类、升级或关闭；大部分告警是误报，需要人工判断后才能关掉。

#### 痛点

- **表现**：六人团队容量有限，分析师只能彻底调查高优先级告警，低优先级告警几乎无人覆盖；分析师大部分时间花在分诊这类机械任务上，而非需要专业能力的判断密集型调查。
- **代价**：低优先级告警覆盖不足，风险敞口长期存在；专业人力被机械工作占据。
- **旧办法**：人工分诊。撑不住在于容量——团队本来就跟不上，不是一支表现良好而被AI扰动的团队。

#### 解法

- **思路**：AI拿走最耗时的机械环节——初始分类与误报过滤，只把需要人工判断的告警升级给分析师；同时把释放的容量明确定义为"向上之路而非出局"。
- **前置**：赞助人条件——技术负责人有完整授权、对其他团队无依赖、把实施当作专门项目运作。
- **链路**（AI分类过滤 → 只升级真警 → 容量再部署）：
1. AI分诊：初始分类与误报过滤，秒级处理告警而非小时级；
2. 升级：只把需要人工判断的告警升级给分析师；
3. 容量再部署：释放的4.5个全职当量明确去向——威胁狩猎、安全架构、能力建设，这些是团队以前从没时间做的高价值工作。
- **机制**：三步化解抵抗——情境（团队已被淹没、低优先级本来就覆盖不了，AI定位为解救而非替代）、分工直观（机械的给AI、判断密集的留人）、路线图具体（什么工作消失、什么留下、什么新工作出现，个人看得到生活变轻松、带宽用于技能升级）。给团队的说法是：AI替代的不是你已有的人，是你不用再招的人——已有的人现在可以做两三个、四个人的工作。
- **落地**：原文未展开实施周期。

#### 效果

- **量化**：告警处理量从每月约1500条升至40000条；高优先级告警覆盖100%；所需团队容量从6个全职当量降至1.5个；释放的4.5个全职当量重新部署，没有任何人被裁。
- **人与组织**：团队从抵抗转向倡导——看到AI是从苦差中的解放，而非对就业的威胁。
- **延伸**：团队获得以前从未有时间投入的高价值方向。

#### 教训与边界

- **弯路**：原文未记实施弯路；预期中的顾虑是岗位安全——六人团队加AI能替代大部分工作负荷，抵抗风险真实存在，被赞助人三步化解。
- **边界**：当前进路径具体化时，对被替代的恐惧会消散；"解救而非替代"的定位成立，前提是团队本来就跟不上——情境做了大部分工作；分工必须直观，机械给AI、判断留人。

### K3.1 非标制造报价：图纸结构化＋规则匹配＋人工校准（FDE NO.17）

#### 背景

- **企业**：柔性制造企业，两三百人，年营收一二十亿元；多品种、小批量，大量订单为非标。
- **业务**：客户先发一张图纸——PDF、CAD或扫描件，含材料、尺寸、关键部位要求、结构要求——企业再判断能不能做、用什么材料、走什么工艺、成本多少、报什么价。"报价"不是算一个数，而是一条完整链路：图纸解析、需求拆解、研发协同、生产方案、成本核算、报价。

#### 痛点

- **表现**：整条链路依赖人工。图纸来了，业务或技术人员凭经验理解客户要求、整理信息，再查企业物料、供应商和历史价格——一个纯人工的理解、结构化、匹配过程。
- **代价**：
1. 占用核心骨干：懂工艺、懂材料、懂可行性的人最稀缺，却被售前方案占满；
2. 影响利润：报高丢单，报低则生产时才发现成本盖不住；
3. 卡住响应：客户询价不等人，骨干正忙时报价积压数日，订单流失。
- **旧办法**：企业早期上过ERP和报价模板，想用固定字段管住流程；但这类系统只能"字段填进去、按规则往下跑"，最难的第一步——把客户五花八门的输入理解成标准数据——没人解决。最后只覆盖标准件和固定SKU，非标部分照样回到人，模板反而多填一遍表。业务量与非标需求上涨后，人的产能不会同比增长，售前链路开始排队。

#### 解法

- **思路**：不让AI直接出价。AI负责把图纸转化为结构化数据，价格由企业自有的物料库与报价规则计算，每一单经人工校准后对外。
- **前置**：进场先复现人工流程——在车间跟踪一张图纸从进厂到报价的全过程，翻阅历史报价单，明确各环节负责人：谁看图、谁拆需求、谁定物料、谁判工艺、谁核成本、谁报价。
- **链路**（图纸进厂后的主线：解析 → 结构化 → 匹配 → 校准）：
1. 图纸解析：多模态模型抽取图纸中的材料、尺寸、结构要求；
2. 结构化：抽取结果转为标准字段——不结构化，无法进入后续业务流程；
3. 规则匹配：结构化需求对接企业物料库、供应商体系、历史数据与报价规则，由垂类Agent串接各环节；
4. 人工校准：业务员核定后对外输出。
- **机制**：校准中的修改回填至数据与模型，形成"生成—校准—回填—再生成"的迭代，人工校准量随数据积累递减。
- **落地**：关键人用真实订单试用；业务小组试运行一至两个月；再部署、集成、培训，扩展至整个部门。

#### 效果

- **量化**：报价相关工作量减少50%以上；原先三至五人参与的环节，人力投入明显减少。
- **人与组织**：释放的人员转向客户开发与项目洽谈；企业随后调整相关岗位的KPI与职责，考核转向业务价值。
- **延伸**：报价能力不再依赖"增加更多老师傅"——业务规模继续扩大时，售前链路可以不随人数同步扩张。

#### 教训与边界

- **弯路**：项目初期曾尝试端到端直接出价，数字与真实成本对不上，遂改为模型只负责图纸信息结构化；上线头两个月处于磨合微调期，并没有立刻达到理想状态——评估标准是结果能否真正拿去报价，不是模型能否输出。
- **边界**：
1. 人工校准不可撤：图纸识别在手写标注、特殊符号、非标准图框上仍会出错，一个尺寸抽错直接影响成本；
2. 数据清洗分量比预想重：中小制造企业的历史报价、物料、供应商信息很少能直接给AI用，还要从数据和老师傅经验里还原"这个物料为什么这样映射、这种情况为什么这样报价"的业务规则；
3. 人的问题比数据难：岗位从三五人变一两人的消息一出，员工第一反应是担心被优化——立项前就要和企业负责人谈定释放的时间往哪转，裁人不是选项；这类转型必须是一把手工程。

### K3.2 消防施工图：规则引擎生成初稿，设计师定案（FDE NO.21）

#### 背景

- **企业**：建筑设计企业的消防施工图业务。
- **业务**：一个常规商业建筑项目，仅消防施工图就可能涉及数百个空间的设施布置——喷淋系统设计、消火栓布置、灭火器配置、管线规划。每处设施的位置、间距、参数都要对照消防规范判断：空间属什么危险等级、选多大K值的喷头、喷头间距是否在规范允许范围内、消火栓覆盖半径是否达标。这不是简单的"画图"，而是逐条执行规范的专业判断。

#### 痛点

- **表现**：
1. 重复操作多：同一栋楼有几十个功能相似的空间（办公室、走廊），每个都重复类似的布置流程，执行性规则占满精力，创造性设计时间被挤压；
2. 规范检查比绘制更耗时：初步布置完成后，还要逐项核间距、核覆盖、核参数；
3. 修改成本高：建筑方案调整是常态，平面布局一变，消防图就得逐处同步改，牵一发动全身。
- **代价**：
1. 效率有天花板：熟练设计人员一天完成的图纸面积有上限，项目集中到来只能加人，而培养一个合格的消防设计人员周期很长；
2. 质量难稳定：不同设计人员对规范的理解和设计习惯有差异，同类空间的布置因人而异，图纸质量不一致，审核环节要额外投入。
- **旧办法**：行业里出现过消防设计插件、参数化工具，但只解决单点问题（如自动计算间距），覆盖不了从图纸理解到成果输出的完整流程，设计人员仍要在多个工具间切换，实际提效有限。

#### 解法

- **思路**：AI负责生成，人负责决策。规范化的布置与检查交给系统，专业参数与最终责任留给设计人员；AI产出定位为"专业可用的初稿"。
- **前置**：通用大模型无法直接理解建筑CAD中的空间关系、图形符号与标注，为此自研专用模型解析图纸——墙体、门窗、空间标注、面积数据。
- **链路**（识别 → 规则 → 分层生成 → 定案）：
1. 图纸识别：解析建筑CAD，提取空间信息与建筑元素；
2. 规则引擎：消防规范条文转化为可执行规则——空间类型决定危险等级，危险等级决定喷头K值、间距、保护面积；
3. 分层生成：常规空间（办公室、走廊）按默认参数一键生成；特殊空间开放危险等级、K值、间距等参数供专业人员调整；
4. 人工定案：关键节点设人工确认，最终图纸由设计人员审核签字。
- **机制**：输出格式严格按设计院交付标准——格式不符合行业标准，内容再对也无法进入流程。
- **落地**：不强行说服，让设计人员在实际使用中体验价值，态度自下而上转变，系统逐步重塑原有工作流。

#### 效果

- **量化**：大型项目从数天缩至约三十分钟出初步结果（项目方口径），设计人员在其上调整确认。
- **人与组织**：设计人员原约七成时间用于绘制与规范检查，该部分转由系统承担，角色从执行转向审核与决策。
- **延伸**：
1. 投标阶段的新能力：过去时间紧只能做粗略方案，现在可短时间产出更完整的消防方案，提升投标质量；
2. 经验工程化沉淀：规范知识与设计逻辑进入系统，团队整体设计能力趋于稳定，不再因人而异。

#### 教训与边界

- **弯路**：用户最初期待"一键生成完整施工图"，设计人员反对——消防图纸的合规与安全责任必须由人承担，不能接受"大概对"的黑箱结果；分层参数与人工确认环节是博弈后的平衡。
- **边界**：
1. 责任边界即使用边界：AI只做规则范围内的生成，不做超出规则的"创造性判断"；
2. 输入决定输出：建筑图纸信息本身不准确，后续一切生成结果都不可靠——基础数据的准确性要单独保障。

### K3.3 工程租赁长尾订单：报价区间＋轻量入口＋订单分层（FDE NO.23）

#### 背景

- **企业**：工程租赁中小企业；行业特点是企业负责人往往身兼唯一销售与唯一调度，多数管理工作压在企业负责人一人身上。
- **业务**：客户结构典型——年营收三千万时，约两千五百万来自几个大客户，五百万来自大量小客户。设备租赁的报价要素不少：租什么车、配不配操作员、油费怎么算、运距多远、运输成本多少、干什么活（作业类型影响折价），叠加起来构成一个复杂的报价判断。

#### 痛点

- **表现**：小订单（十万元左右）金额不大，报价时企业负责人同样要把需求、车型、运输成本、人员、油费过一遍才能定价——他正谈一个大客户时，小订单只能放掉。
- **代价**：上行期，长尾的五百万可以不管——企业负责人精力有限，小客户丢了就丢了；下行期，这五百万随时消失——企业负责人有客户，却没有能力全部接住。问题最终落在企业负责人的时间分配上：最该做高价值客户的人，被大量低价值但不能放弃的订单占用精力。
- **旧办法**：企业负责人亲自谈、亲自报价——大客户价值高、价格不透明，由企业负责人判断反而是最优解，增长期一直运行良好；瓶颈只出在长尾——环境转差后，这个原本合理的分工接不住小客户了。

#### 解法

- **思路**：订单分层。大客户不交给AI——价格不透明、单值高，由企业负责人亲自判断；标准化小订单由系统承接，AI完成前置沟通与初步报价。
- **前置**：先梳理完整链路——客户从哪里来、如何询价、哪些订单必须企业负责人处理、哪些可以标准化；获客入口一并纳入设计，采用抖音、快手、小程序等轻量入口，不要求客户安装App。
- **链路**（需求 → 区间 → 沟通 → 分流）：
1. 需求收集：系统通过轻量入口收集小订单需求；
2. 区间报价：按车型、操作员、油费、距离、作业类型计算报价区间；
3. AI沟通：判断订单能否快速成交，数分钟内出结论——可成交进入调度，不可成交放弃或转人工。
- **机制**：一线员工不更换工具。员工偏中年、不习惯小程序的，前端做到足够简单，语音、微信机器人均可——方案未必技术最优，能在真实业务中运行是第一标准。
- **落地**：从一个能看见结果、试错成本低的小点切入做概念验证，跑通后再逐层扩展。

#### 效果

- **量化**：无可报百分比——项目早期，实际运行一个多月；已落地各点上，客户对效率提升的感受比较明显，认可结果后才愿意继续往下做。
- **人与组织**：企业负责人的精力回归高价值客户与决策；长尾订单从"没人接"变为系统前置承接。
- **延伸**：价值按三层看——效率（AI前置判断）、增收（长尾接住即新增收入）、企业负责人带宽；商业模式在探索：年维护费之外尝试过增收分成，但分成基数难以量化，不易泛化。

#### 教训与边界

- **弯路**：客户口头描述简单的需求（"建一个库加一个搜索"），实施成本难以预估——数据库怎么搭、数据怎么清、量有多大，都藏在后面。
- **边界**：企业负责人本人不使用，项目无法推进——一号位的使用意愿是硬前提；方案不强求"纯AI"，模型、业务规则、运筹学混着用，能解决问题就行。

### K3.4 电商内容生产：一致性验收＋人审终关，素材沉淀为资产（FDE NO.12）

#### 背景

- **企业**：传统鞋服帽电商企业，有自己的工厂和设计师，主要在淘宝、天猫等平台销售，行业里已属头部，年流水大概10亿元，长期养着一支规模不小的设计和运营团队。
- **业务**：SKU非常多、新品上得很快，每上一个新品都要商品主图、详情素材，视频电商起来后还要配套挂车视频——内容生产量成倍增长。

#### 痛点

- **表现**：员工各自开AI账号、自己写提示词，使用方式分散；设计师审美、经验和AI使用能力不一样，产出参差；图片视频散落在个人电脑里。
- **代价**：
1. 人力成本高；
2. "看起来都用上AI了"，实际只是把新工具塞进旧流程，操作成本没有真正消失，效率没有质变；
3. 品控不能建立在几个高手身上；
4. 内容没变成公司资产——一个人离职换岗，素材就断。
- **旧办法**：一是设计师加运营团队人肉支撑，本身有效、已把业务做到很大规模，但内容产能和人力数量强绑定，想扩供给只能加人；二是让员工各自用AI提效，从"人做图"变成"人盯着AI做图"，还得反复调整，且把人的差异继续放大，谈不上稳定的生产能力。

#### 解法

- **思路**：把散在个人手里的AI使用重构成公司级、可复用、可管理的素材资产生产线；项目原则是"AI负责规模化，人负责最后的业务判断"。
- **前置**：先到现场，不急着做产品：识别关键干系人——企业负责人关注战略转型长期价值、管理者关注成本效率、基层员工担心增加工作量或被裁；观察员工每天干什么、上下游怎么协作、大量时间耗在哪里；先解决小麻烦破冰，如生图要写很长的提示词、生成完还有水印要再处理。
- **链路**（调研与Demo → 重搭工作流 → 一致性验收）：
1. 调研与Demo：数据采集、工作流梳理、访谈挖真实需求，不花几个月先做"大而全"的产品；借助AI快速做Demo拿给客户看，反馈沉淀进文档、由客户在指定位置持续填写；
2. 重搭工作流：AI生成与商品、素材和企业原生产流程连接，生成的图片视频直接沉淀为公司级素材资产，商品进入统一的商品管理逻辑；
3. 一致性验收：把"好看"变成"能商用"——一致性写进验收标准，分人物一致性、服饰一致性、场景一致性三个层面，达到要求才算通过；AI先做第一道检查，再交人工确认。
- **机制**：审核保留人工环节；验收覆盖还原度、图片质量、视频能否商用及一致性；反馈持续填写，滚动进迭代。
- **落地**：核心功能完成后进入POC阶段，推动企业内部员工真正使用——光自己坐在那里测不算数——收集优化和改动意见继续迭代。

#### 效果

- **量化**：无可报数字——项目仍处于POC测试、内部试用和持续迭代阶段。
- **人与组织**：验收标准从项目团队自己的感觉，变成设计师有没有把能力用起来、和原工作流契不契合；内容从个人产出变成企业资产，生成、管理和后续使用进入统一流程；AI生产有了明确的质量边界，效果不再高度依赖某一个人的水平。
- **延伸**：企业开始形成稳定、可控、可沉淀、可继续扩大的内容生产方式——原文称这才是真正想验证的价值主张；同时有意识沉淀"家底"，商品中心、订单中心、用户中心等电商最基础的通用能力，未来可直接复用。

#### 教训与边界

- **弯路**：一开始容易把问题想简单——"设计师出图太慢，就用AI帮他出图"。
- **边界**：
1. 最大挑战不在模型本身：客户对AI的认知两个极端——一种觉得"现在挺好，为什么要折腾AI"，一种觉得AI无所不能、期待"花10万元就应该做出100万元的效果"，要反复强调把AI放进真实产业场景里跑；
2. 基层员工怕被取代，情绪不解决，拿到的需求可能是假的、上线没人用——不讲"AI转型"大词，先解决眼前小麻烦建立关系，再说清目标是帮大家从低价值重复劳动中脱身；
3. 生成内容最怕"看起来很好但商品不对"——验收标准拉回业务本身，硬性要求一项不松；不能因为用了AI就把审核完全自动化，最终业务责任交给人。

### K3.5 本地生活文案量产：经验拆成字段，AI先跑、人判断（FDE NO.15）

#### 背景

- **企业**：抖音本地生活代运营，客户以餐饮商户为主、覆盖多个城市，内容需求量非常大，最高峰一天需要产生两三百条文案。
- **业务**：为商户持续产出短视频文案与脚本——同是餐饮，商户差异很大：高端酒店、连锁餐厅、独立小店，主打菜品、活动、老板表达方式、目标客群都不一样。

#### 痛点

- **表现**：每天要写大量文案且不能写得太差；内部不缺会写的人，但能力难被规模化复制——一个人不可能每天稳定处理几十甚至上百条内容；通用模型按固定模板生成，很难照顾商户之间的差异。
- **代价**：好的内容靠人，规模化生产离不开人，人本身就是瓶颈。
- **旧办法**：一是运营凭经验生产（有人写文案、拍摄、剪辑，负责人协调审核），客户不多时能运行；但什么老板适合什么表达、什么菜品该突出什么卖点，都存在人脑子里、没有沉淀成标准化文档，规模上来后难继续放大。二是直接让AI写，包括本地部署DeepSeek，效果没有达到预期——AI味很大程度来自"固定范式"：给AI一套固定模板让它不断模仿，单个案例里可能有效，面对不同商户、题材、场景时就机械地重复。

#### 解法

- **思路**：先假设AI能做，再通过实际测试把做不到、做不好的部分逐渐交还给人；AI负责大部分标准化生成，人负责最后的审核和判断。
- **前置**：把业务真正看懂。现场观察实际工作流程——谁负责什么、新客户怎么进来、运营怎么判断一条文案好不好、不同商户哪些地方会变化——把原来依赖人的工作方式沉淀下来；业务流程没有被很好地数字化和结构化，不解决就把历史资料扔给AI，落不了地。
- **链路**（经验拆字段 → 组装生产流程 → AI先跑、人判断 → 反馈调优）：
1. 经验拆成字段：不同商户文案风格不同，底层关注的东西接近——客户是谁、门店什么类型、主推什么菜品、有什么活动、突出什么卖点、什么内容方向——变成相对明确的输入字段，把优秀运营脑子里的经验变成系统可调用的业务逻辑；优秀文案人员的写作方式、技巧和参考案例也融入工作流；
2. 组装生产流程：一个Prompt或一个Skill不够——"写出一篇文案"和"稳定地生产可使用的短视频脚本"是两回事——把提示词、Skill、业务参数和校验、审计等Loop机制组合起来；文案还要考虑拍摄时的节奏、声画配合，形成可直接拿去使用的脚本框架；
3. AI先跑、人判断：不追求整个流程百分之百自动化；某节点AI做得不好，就把该节点交还给人（回退机制）；
4. 反馈调优：周期性提供不同版本，结合平台数据反馈——"这个味道不对"、某时段留存下滑、某些客户或SKU下不稳定，就把反馈带回来调整；对象可能是提示词、系统逻辑顺序、关注点，甚至模型选型。
- **机制**：回退机制保底，不稳定节点随时交还人工；交付时预留迭代空间，客户按照SOP自己继续优化，项目结束后事情不会回到FDE这里。
- **落地**：用对比开局——客户原来的结果与AI跑的一个小Demo放在一起比较；AI达到一定水平就继续走，某环节不稳定就调整或保留人工。

#### 效果

- **量化**：无具体数字；原文定性口径"从客户的使用反馈来看，效果非常明显"。
- **人与组织**：原来大量工作依赖少数经验丰富的员工，现在AI承接相当一部分重复性生成和适配；过去只有少部分内容让客户比较满意，现在AI把大量内容先做到相对稳定的基础水平，再由人筛选优化；新客户进来提前规划好门店、主打菜品、活动等参数，系统持续生成，把堆积在某一天的人力需求提前消化（"削峰填谷"），生产不再卡在"一个人每天能处理多少条内容"上。
- **延伸**：一套业务逻辑具备进一步复用的可能——不同餐饮客户最终文案不同，但背后的字段和基本Know-how范式相通，具体取向通过参数调整。

#### 教训与边界

- **弯路**：客户此前直接让AI写、本地部署DeepSeek，效果没达预期；"人工写→AI写"的简单替换被放到一边。
- **边界**：
1. 最大难点不是开发，挑战在文案之外：几百字的文案做成短视频，背后是人物怎么讲、情绪怎么表达、画面怎么配、节奏怎么样；客户觉得"这个不对"又说不清哪里不对，要把模糊反馈转成可调整的提示词、流程或判断标准；
2. 稳定性随对象变化：设计好的提示词在一个案例里表现不错，换一个商户或SKU就可能出现偏差，要回到具体业务看是输入信息不够，还是参数、提示词或流程要调整；
3. 运营要学会和AI协作——把业务要求转成系统能理解和复用的输入、把"味道不对"的主观反馈变成系统能吸收的反馈，这是新的工作方式。

### K3.6 营销内容80/20：AI生成八成，人精修两成（斯坦福·营销内容）

#### 背景

- **企业**：金融服务公司，营销职能，企业级规模；具体人数原文未提。
- **业务**：面向客户做多渠道营销内容，手里握有可用于超个性化的客户数据。

#### 痛点

- **表现**：内容生成速度跟不上——手里有可做超个性化的客户数据，却无法利用；内容生产走传统代理机构工作流，每个campaign要七周。
- **代价**：每个campaign七周的时间成本；有客户数据用不起来（具体金额原文未提）。
- **旧办法**：传统代理机构工作流——生成速度跟不上，无法利用客户数据做超个性化。

#### 解法

- **思路**：80/20分工——AI处理80%的生成，人提供20%的精修与质量保证。
- **链路**（多渠道生成 → 人工精修 → 反馈回授）：
1. 多渠道生成：部署AI平台，生成多渠道内容，同时保持品牌一致性；
2. 人工精修与质量保证：人工层承担品牌保护——防住会损害多年品牌建设的错误；边缘案例处理——处理需要判断力的不寻常组合；
3. 反馈回授：审校者识别可改进AI产出的模式，形成反馈回路。
- **机制**：企业级面向客户的内容零错误容忍，20%人工押在品牌保护、边缘案例与反馈回路三件事上；随技术成熟和经验积累，交给AI的百分比最终趋向100%。

#### 效果

- **量化**：campaign上市时间从七周缩至六小时；点击率改善2倍；生产时间减少超过80%。Key Lessons口径：80/20模式交付97.6%的上市时间缩短，同时保持零错误容忍。
- **人与组织**：人工监督不是生产力的税，分工是刻意设计——企业级营销对面向客户的内容不能容忍错误。企业AI公司战略负责人的原话是：要跑到企业级，需要80%的技术加20%的人做精修，AI行业还没有达到能拿下最后那20%的水平。
- **延伸**：公司把20%的人工成分视为过渡性安排，预期随AI改进而减少；但起点是"现在能用的"，而不是等待完美的自动化到来。

#### 教训与边界

- **边界**：
1. 监督水平应与风险相配：企业级面向客户的内容零错误容忍，因此保留20%人工；
2. 80/20是设计选择，而非对AI不成熟的让步；20%人工是过渡安排——从可行方案起步，不等待完美自动化。

## 第四类　系统串联：人不再当搬运工 {#appK-4}

这一类方案针对系统之间的信息割裂：数据在多个系统里靠人搬、人抄、人对，人成了系统之间的连接件。解法方向一致——把整条业务链上的搬运环节逐个换成自动化与Agent，人只守关键节点；差别在于链路长短与守的位置。

| K4.2 跨境电商链路：数据自动流动，人不当连接件（FDE NO.22） | 人当系统连接件，一边烧广告一边发不出货 |

### K4.1 达人建联运营：AI先筛先配，商务关系留人（FDE NO.5）

#### 背景

- **企业**：国内头部电商企业在海外TikTok生态里的达人建联业务（TAP，类比"团长"：商家有新品或营销节点时找TAP，TAP从自有达人资源里筛人，推动接品、拿样、创作，把商品挂到达人账号上）。
- **业务**：链路为达人进入→达人建联→选品匹配→拿样、创作、履约→数据复盘；选品池里有上万个商品，旧方式下一个运营每天维护几十个达人。

#### 痛点

- **表现**：找达人像"大海捞针"；上万个商品对达人不同的内容标签，什么商品推给什么达人本质上是匹配问题；确定合作后的寄样、创作、提交，平均履约周期约一个月，运营大量时间花在"催"上；数据一部分在TikTok、一部分在Excel、一部分在财务系统，企业负责人想看一个达人从建联到GMV的完整经历并不容易。
- **代价**：
1. 运营人员大量时间花在找人、找商品、找任务上；
2. 管理者很难及时看到整个业务漏斗。
- **旧办法**：业务规模不大时靠人——一个运营每天维护几十个达人，自己记得住谁聊到哪一步、谁收了样品、谁还没拍视频，配合飞书和Excel业务就能正常运转。撑不住在规模：选品池从几百个商品变成上万个，不可能再靠经验一个个匹配；达人越来越多，人工翻Excel催不过来。

#### 解法

- **思路**：把整条链路拆开重新分工——筛选、匹配、脚本、催办、数据串联交给AI与系统，与达人的商务沟通和关系建立留给人。
- **前置**：客户最初问的是"我们团队怎么用AI赋能"，先反问业务到底怎么跑、哪个环节最慢、谁每天最累、哪里最容易出错；从企业负责人到部门负责人再到小组负责人基本访谈一遍，把流程画出来，逐环节看哪些必须由人完成。
- **链路**（筛人 → 配品 → 出脚本 → 催办 → 串数据）：
1. AI筛人：按商品信息、达人标签、内容属性先筛出一批更值得关注的达人，给BD一份更精准的名单——BD从寻找目标变成直接和目标沟通，发消息与建立关系保留人工；
2. AI配品：把商品卖点（口味、气泡、品牌、联名）提取出来，与达人的内容属性匹配，AI先筛、人再判断；
3. AI出脚本：很多达人的卡点是拿到商品后不知道"怎么拍"，系统把达人特点、商品卖点、爆款内容参考结合起来给几个可选拍摄脚本——客户反馈，目前达人对这部分能力接受度比较高；
4. 系统催办：按履约状态自动判断谁已收样、谁快到截止时间、谁超过提醒仍未动作，先自动提醒，仍不履约再交给人工运营；
5. 数据串联：建联、履约、商品、GMV等数据放进统一的业务视角，管理者据此判断一个达人值不值得长期合作。
- **机制**：系统把需要人工介入的任务主动拉出来；运营的时间转向和达人沟通、建立关系、处理复杂商务问题，高价值达人身上变化更明显。
- **落地**：先现场访谈、流程拆解，再进入试运行；更细的推广节奏原文未展开。

#### 效果

- **量化**：过去从确定合作到达人收到样品、完成创作并提交视频，平均大约需要一个月；项目试运行之后，目前配合的达人平均履约时间已经到了约18天。
- **人与组织**：管理者开始真正看到业务，可围绕"达人—履约—GMV"形成更完整的业务视角——以前团队是在管理一堆表格，现在是在管理一条业务链路。
- **延伸**：AI落地在做的是重新组织人的工作方式，这是与普通自动化的重要区别；未来可探索AI视频生成。

#### 教训与边界

- **弯路**：项目数据大量来自TikTok且涉及跨境业务，数据权限、用户隐私、数据留存和服务器部署都有严格要求，光数据这一块就花了接近一个月——数据申请、权限账号、数据能不能离开所在国家都要提前搞清楚。
- **边界**：
1. 达人匹配、名单初筛、履约提醒可以交给AI和自动化，与重要达人的沟通保留人工——AI仍可能犯一些很低级的错误，对象若是拥有几百万粉丝的达人，一句话说错的损失可能远远超过自动化节省的人力成本，这也是最终没有做"全自动达人建联"的原因；
2. 推进时把AI定位明确成"帮助大家解决问题、提高效率"；访谈不能只找企业负责人——真正使用系统的是一线员工。

### K4.2 跨境电商链路：数据自动流动，人不当连接件（FDE NO.22）

#### 背景

- **企业**：跨境电商团队，主营东南亚市场、服装，10～15人。
- **业务**：服装每个颜色、每个尺码都是独立SKU，按访谈中的估算每季度新增500～800个SKU，全年SKU大概2500～3000个；整条业务链为订单库存→物流数据→补货决策→供应商下单→广告投放；库存数据集中在多平台聚合SaaS里，新品开发、部分业务信息又在飞书里。

#### 痛点

- **表现**：客户最初只说"能不能把这个多平台聚合SaaS和飞书打通"，真正要解决的是链路上的信息割裂——工厂发货没用RFID或扫码枪，仍靠拍照、识图，员工人工看照片、填数据、追物流单号；补货要从SaaS里扒数据、填进自己的计算表、按公式算完誊进另一个模板、生成PDF发供应商；某SKU库存已经很低，广告还在继续跑，客户继续下单，企业却发不出货。
- **代价**：
1. SKU从几十个、几百个涨到几千个，人一天的时间大量耗在"看、抄、填、核对"上，规模越大人越被钉在搬运动作上；
2. 一边烧广告一边发不出货；
3. 每件事单独看不重，连成一串是非常长的人工链路。
- **旧办法**：Excel、聚合SaaS、飞书都在转，靠一个人来回搬数据，规模不大时应付得过来；补货有一套自己的公式（看SKU过去三个月的销售加自己的预测逻辑），这套逻辑是成立的。撑不住在SKU涨到几千个人盯不过来——工具没换，人在当中间连接件。

#### 解法

- **思路**：不当API集成项目做，沿整条链路一步步把人工搬运环节换成Agent——工具不换、公式不换，每一步留人工确认。
- **前置**：连续开几次会、让客户录屏演示实际怎么工作，才发现库存只是整条链路上的一个环节；大概花了一周、三四轮沟通把场景收集起来，再讨论哪些适合自动化、哪些接Agent、哪些不需要AI。
- **链路**（通数据 → 识图回填 → 算补货 → 库存反制广告）：
1. 通数据：把聚合SaaS的数据同步到飞书，让客户在熟悉的业务环境里看到实时库存；对方SaaS的API开放程度很低，Key有失效机制、满足不了多团队共享（A团队刷新Key，B团队就失效），这是全项目最难啃的技术问题，最后加一层开源云端数据库（Supabase）做中转；
2. 识图回填：Agent参与物流照片的识别与数据录入，保留人工确认——AI做原来最耗时的第一轮，人只做最后检查；
3. 算补货：数据直接进入业务流程，Agent按原补货规则计算，筛出需要补货的SKU并给出预计周期和数量；人工从"计算员"变"审核员"，确认后直接生成PDF订单发给供应商；
4. 库存反制广告：把库存、订单、广告投放结合，某SKU库存降到一定程度，Agent判断对应广告是否还该继续投，不足就先调低额度、甚至暂停。
- **机制**：不追求100%无人化——识图后人工核对、补货后人工确认、广告调整基于库存做业务判断，人的时间流向更需要判断力的地方。
- **落地**：从打通库存这一个环节起步，沿链路逐环节接Agent。

#### 效果

- **量化**：物流照片处理以前一个人每天大概4～5个小时看图片、写数据，现在AI先完成识别和回填、人只做最后核对，整体时间压缩到1小时以内；补货以前至少2～3个小时，现在Agent把结果算出来，工作人员看一眼、验证后生成订单。口径限定：交付结束后客户把团队权限移除了，后续的营收、广告成本和利润数据没有拿到完整的。
- **人与组织**：三个变化——从"人工搬数据"变成"数据自动流动"，从"人工计算"变成"AI计算、人工确认"，从"库存、补货、广告各自决策"变成"库存开始影响广告决策"。
- **延伸**：业务开始从单点自动化走向流程之间的联动，FDE认为第三点比单纯节省几个小时更重要。

#### 教训与边界

- **弯路**：最大遗憾是交付后没有把效果完整追踪下来——如果重新做，会在一开始设计好效果基线，上线前后持续记录关键指标；"有API就可以接"想得太简单，卡点在Key机制，最后靠加一层中转解决。
- **边界**：
1. 客户说出来的需求不一定是真正需求——说的是"打通两个系统"，真问题是照片处理、补货、供应商下单、广告投放一整串；
2. 现实里的AI落地很多时候卡在模型之外，原有系统的开放程度、数据结构和接口限制才是真正的门槛；
3. 先判断需不需要AI——规则非常死的任务写脚本就够，涉及语义理解、跨系统判断才引入Agent。

## 第五类　从看不见到看得见：先攒数据，再串经营视角 {#appK-5}

这一类方案针对"看不见"：数据没有、散落各处，或者有了却串不成管理者要的经营视角。解法方向一致——先把数据攒起来，再按经营逻辑串成视角、异常主动上报。四个案例里，前两个从补数据地基起步，后两个在已有系统上重组。

### K5.1 消防维保：监管流程之上轻改，先攒数据再点状上AI（FDE NO.13）

#### 背景

- **企业**：消防维保企业，承接物业等客户的消防检查、维护和维修；规模不算特别大，业务稳定，典型传统行业，大量线下执行环节。
- **业务**：维保人员到客户现场执行检查维修，按监管要求记录留档；日常运转靠经验驱动——企业负责人靠行业经验判断，员工靠熟悉流程工作。

#### 痛点

- **表现**：数据割裂——检查记录在纸质表格、维修记录在Excel、客户信息在某人的微信聊天记录、设备档案散落不同文件夹，按监管要求保存了，但没有形成统一体系；企业负责人看不见一线，只能靠周期性汇报，哪些项目执行到位、哪些客户风险未处置、影响回款的记录因人员变动遗失，都要再问人；一线人员大量时间耗在业务之外——填表、整理Excel、打印归档、反复沟通确认，有时一张表的填写和整理就占用半天。
- **代价**：一线时间纯消耗，不产生直接业务价值；数据查找困难，无法支持管理决策；行业利润空间持续下降时，经验驱动模式短板暴露，影响新业务拓展。
- **旧办法**：去年曾与外部团队合作引入过一个监控平台，内部没有形成完整的数据体系和流程系统；直接购买大型系统成本难负担，外部方案功能列表完善却不理解现场监管流程和实际执行方式，最坏情况是系统上线变成员工额外的一套操作，不减负反加重负担。

#### 解法

- **思路**：不另起炉灶——在已有监管流程之上做最轻量的数字化改造，先把数据攒出来，再只在真实存在业务成本的环节点状引入AI。
- **前置**：进现场。与维保人员、人事、行政、财务逐一沟通，观察怎么填检查表、资料怎么流转、哪些环节反复确认——只做管理层访谈，容易拿到看起来正确但偏离核心问题的需求。现场还纠正了原方案的方向性错误：企业已部署政府监管要求的软件流程且无法开放接口，再建完整系统意味着员工在两套系统间重复操作。
- **链路**（数字化 → 筛介入点 → AI辅助）：
1. 流程数字化：纸质表单和Excel里流转的数据迁到线上，让信息能被记录、沉淀和管理，先让企业拥有数据基础；
2. 筛选介入点：先问业务流程中哪里存在真实的业务成本，再判断该环节是否适合AI介入；
3. AI辅助生成：月检表中某些设备长期存在相同异常，每月都要复制粘贴几乎一样的描述——AI辅助生成和调用历史记录，减少重复劳动。
- **机制**：系统负责流程记录和数据沉淀，AI负责处理复杂信息、辅助生成，人负责最终判断和业务决策——消防专业判断必须由人来做。
- **落地**：用飞书等企业已有的基础工具，小模块、小功能逐步迭代；流程设计兼顾企业负责人的数据透明和员工的流程负担，双方诉求同时满足才可能被使用。

#### 效果

- **量化**：无经营指标数字——原文口径为项目仍处持续推进阶段，尚未形成大规模的业务指标变化。可计的一项是避免一次无效投入：企业原考虑花约10万元采购一套外部业务系统，现场调研发现该方案没考虑行业监管流程和实际执行方式，采购被叫停。
- **人与组织**：管理从高度依赖企业负责人个人直觉，转向逐步拥有自己的数据资产，管理者更清楚哪些项目在执行、哪些环节存在风险；维保人员从重复填表整理中释放，时间投入真正的检查和维修，交付质量和客户满意度随之提升。

#### 教训与边界

- **弯路**：原计划建设完整的业务平台，没发现已有政府监管流程无法开放接口，靠现场观察才及时调整；正式访谈中一线需求失真——外勤维保人员平时很少回公司，坐会议室面对企业负责人和管理人员有压力，只被动回答被问到的问题。
- **边界**：需求不靠会议室访谈，从现场流程反推真实痛点；从业务成本出发判断AI介入点，简单流程优化能解决的不一定需要AI；避免过度建设，完整方案与最小可用功能之间选务实路径，简单方案更容易落地、更容易根据反馈调整。

### K5.2 生物科技销售线：先补CRM和数仓，AI再进场（FDE NO.18）

#### 背景

- **企业**：生物科技上市公司；销售部门是4维模型筛选出的第一个先行试点场景，直销加渠道200多人，专业门槛高，一线人员流动不低；企业有ERP有OA但系统老旧、数据不通，HR的人事资料还停在纸质文件柜里。
- **业务**：客户关系散落在销售个人手里，谁有哪些客户、进展到哪一步，公司层面很难掌握；销售大盘、业绩、提成靠Excel人工统计；新人培训靠线下培训会加老带新手把手教；招聘靠HR和老销售一起筛简历面试。

#### 痛点

- **表现**：管理层想实时看销售大盘，数据延迟1个月以上是常态，动态分析基本做不到；提成计算量大、环节多、效率低、准确率有限；人一走，客户线索跟着流失；新人要懂行业法律法规、行业规则和大量销售话术，培训周期接近两个月；招聘面试消耗老销售时间。
- **代价**：高价值的人被低价值的事占用，培训和招聘都压在业务人员身上；管理层看不清经营；销售的数据、系统、人才和认知还没准备好——它不可能是接上模型就能上线的单点应用。
- **旧办法**：业务规模不大时，人工维护客户、Excel算提成、老带新培训、人工筛面能把事做完；但系统老旧、数据不通，大量关键数据退回Excel和个人手里；要实时看区域趋势、分析涨跌原因时撑不住——原来的信息化能力承接不了新的战略目标。

#### 解法

- **思路**：AI转型的第一步发生在AI之前——先补信息化和数据基础，再让AI进经营分析、培训与招聘，同时帮企业自建AI团队把能力留下。
- **前置**：进现场做诊断——逐个部门访谈，看业务流程、系统、数据和真实痛点；纸面台账和人工计算随处可见。诊断原则：不要看到一个问题就马上判断它该用AI——销售提成本质上是信息化和数据问题。
- **链路**（补数据 → AI+BI分析 → 提人效 → 建团队）：
1. 补数据基础：先帮企业选购CRM，把散落在销售个人手里的客户、订单、绩效数据统一进系统，再结合数仓逐步汇总——这一步看起来不像AI，但决定了后面的AI能不能真正进入业务；
2. 经营分析：先通过BI把经营数据转化成销售大盘，再让AI参与分析不同大区趋势、涨跌原因；销售日报、周报和客户拜访记录也结合进来，辅助管理层经营调整；
3. 培训与招聘：AI陪练和电子化考试串成一套完整闭环，边用边按新人通过率优化；招聘端做AI简历筛选、打分，并试点自动化一面；
4. 自建团队：第一阶段后建议董事长扩充内部团队，企业拿出20个编制，FDE参与人员招聘和团队框架建设。
- **机制**：数据分阶段治理——先把最关键的数据跑通，再逐步把其他数据接进来，边接入边治理；培训闭环按新人通过率持续调整。
- **落地**：场景从业务最痛的地方筛——问题有多痛、一年发生多少次、占用多少人、影响多少收入或成本；销售线优先，正因离收入近、痛点集中。

#### 效果

- **量化**：新人培训周期从接近两个月缩短到大约3周——对200多人、流动不低的销售团队，新人更早进入有效销售状态；招聘端测算一个老销售每月在筛简历、面试上投入3-4个人天，引入AI筛选打分后基本能省下来——拿回这些时间至少可以多拜访1-2个客户。
- **人与组织**：管理层除了看到销售结果，还能更快看清各区域趋势以及增长、下降背后的原因，更快做经营调整；被AI释放出来的时间重新变成企业的生产力。
- **延伸**：项目从帮企业做几个AI应用，变成帮企业建立继续往前走的能力——企业后续自持算力和行业小模型，FDE协助主导20个岗位的招聘和团队搭建。

#### 教训与边界

- **弯路**：培训环节一开始想直接建知识库、新人就能用，真正跑起来发现还要和考试、上岗标准、组织方式结合；走进去才发现业务领先和数字化领先完全是两回事——销售数据散落在不同系统和个人手里，直接上大模型很容易变成一次性的演示。
- **边界**：销售数据散时接受现实、不跳过信息化和数据化——该补CRM就补、该建数仓就建；数据治理难——来源杂、口径不一致，等于一边清理历史数据一边重建业务流程；销售团队对AI有恐惧——高层先明确为什么做AI，再跟中层讲清楚收益、岗位和职责怎么变，不能一上来把AI和裁员绑在一起。

### K5.3 制造经营透明：不换ERP，AI当数据关系处理器（FDE NO.20）

#### 背景

- **企业**：汽车供应链企业，向下游销售汽车维修零部件；生产形态偏轻——主要从上游采购零部件，做简单加工、组合、组装后交付，跟传统重生产线的制造企业很不一样。
- **业务**：已用管家婆这类标准化ERP，订单、生产任务、采购、库存、发货数据都有。

#### 痛点

- **表现**：数据都有，企业负责人还是看不清——系统里的数据没有按企业负责人的经营逻辑串起来；他关心的是生产任务有没有正常推进、采购有没有多订、库存到底有多少、什么时候能发货、财务要付供应商的钱对应哪些客户订单。典型例子：供应商发来5000个扳手，实际只发4980个、少了20个；按原ERP标准逻辑，数量没达到5000个订单可能无法正常入库，而现实业务不会因少20个把4980个退回去——标准逻辑无法表达"实际发生了，但标准流程没有完整结束"。
- **代价**：企业负责人想知道真实情况得再去问人；这类问题靠人工处理，意味着员工需要额外记录、解释和沟通——企业负责人希望企业尽量自动化运行、异常主动通知，而不是每天盯工厂、依赖人工询问。
- **旧办法**：管家婆这类标准化ERP本身能看到订单、任务单、采购、库存、发货信息；ERP解决的是标准化信息管理问题，企业负责人需要的是更贴近经营的判断视角；SaaS产品为保持标准化和商业ROI，不会针对每家企业的经营方式做大量深度定制——于是数据都有，还是看不清。

#### 解法

- **思路**：不换ERP、不重新开发，保留原系统，让AI当"数据关系处理器"——把各环节数据按企业负责人的经营逻辑串起来，异常主动提醒。
- **前置**：先拆企业负责人的经营诉求，不急着写代码：不问"你想要什么AI功能"，改问"你每天最担心企业发生什么""哪些事情你必须亲自盯""哪些异常一旦发生你希望第一时间知道"；项目过程含大量数据清理、数据治理和口径整理。
- **链路**（取数重组 → AI匹配关联 → 异常提醒）：
1. 数据重组织：保留原ERP，把必要数据拿出来重新组织、二次加工；
2. AI匹配核对：过去大量靠人工的数据匹配、核对和关联交给AI——判断不同业务环节之间是什么关系、对不对得上；例如财务要付供应商10万元，过去要人工对应供应商订单、客户订单、库存签收来回答为什么，现在由AI做匹配；
3. 异常主动提醒：给关键业务节点设置判断标准——价格是否合理、库存数据是否异常、应付款能不能和相关业务数据对应起来，一旦异常通过飞书卡片提醒相关人员。
- **机制**：形成闭环——正常情况自动运行，数据持续匹配核对，发现异常主动提醒，人处理异常；企业负责人从逐条问人里解放出来。

#### 效果

- **量化**：无可报数字——原文口径：项目目前上线时间还比较短，现在还不能证明企业的利润、成本或者其他经营指标已经发生了明确的量化提升。
- **人与组织**："有数据但看不清"的情况重新呈现——4980个扳手现在可以告诉企业负责人实际库存已增加4980个，系统开始更接近真实业务；财务应付款可追溯，能追溯这笔钱对应哪些客户订单、哪些上游采购；企业负责人想要的"企业能够尽量自动运行""出现异常能够通知他"，目前基础功能已实现。
- **延伸**：完成了从"有没有这个功能"到"经营信息能不能被看清楚"的第一步；减少重复订货等更进一步的经营效果，还需继续运行一段时间才能验证——FDE不把刚上线的项目包装成已产生巨大经营收益。

#### 教训与边界

- **弯路**：曾想把这套方案直接复制给其他制造业企业，做下去发现即便同行业、规模差不多的企业，底层的数据基础、数据口径、业务流程都可能差很多，最后没有急着包装成标准化产品。
- **边界**：企业负责人的认知要先对齐——既理解他的经营逻辑，也让他知道AI能做什么、不能做什么；行业Know-how是进入业务现场的门票，不必成为最资深专家，但要知道行业基本怎么运转；数据是本案无法直接标准化复制的主要原因——方法论可复用，底层数据和业务逻辑未必能复制；ROI上真实企业场景要问"做到80分划不划算"，需大量人力做数据治理、长期维护和定制开发的项目，对FDE团队不一定是一门好生意。

### K5.4 海外动销：AI嵌进原有系统，数字溯得回源头（FDE NO.24）

#### 背景

- **企业**：澳洲一家头部乳企（做奶酪），通过经销商模式进入中国和越南市场；总部负责品牌、供应链和产品，经销商负责当地销售和渠道运营——总部在这两个市场一个零售触点都没有。
- **业务**：总部把货卖给经销商（Sell In）；消费者最终买走多少（Sell Through）更能反映真实市场需求和营销投入效果，但跨境场景下最难获得；信息靠人工流转——经销商用Excel、邮件反馈，中间经过语言转换、业务解释和数据整理。

#### 痛点

- **表现**：货发出去，过了国境就断了——总部只看得见发货，两国动销是黑箱。数据标准不统一——Excel、PDF、图片甚至手写凭证，字段、销售单位、促销规则都不一样；市场费用、营销费用靠人工审核——企业知道需要管理，但没有足够的人力。
- **代价**：信息滞后——总部看到的数据可能已经是几周甚至更久之前的；数据失真——"销售情况怎么样"不同角色理解不同，口径从一开始就可能错；人工成本高——大量时间花在整理数据、开会解释、沟通确认，市场业务反被搁置。人工审核市场费用能发现的问题比例不到10%。
- **旧办法**：总部发货、经销商整理销售数据、业务人员翻译整理再反馈总部——经销商规模有限时有效。曾引入BI工具和报表系统：BI只能处理已结构化的数据，海外原始数据恰恰是非结构化的；上线后清洗整理仍靠人工，只是换了个地方看Excel——把两份不可比的数据画成漂亮的图，让不可比更隐蔽。

#### 解法

- **思路**：不建新平台，把AI当一层能力嵌进原有系统；流程从"人工传递 → 人工整理 → 人工审核"变成"AI抽取 → AI校验 → 风险标记 → 人工最终审核"。
- **前置**：进现场重新梳理业务流程——观察总部怎么接收、核对、开会，远程了解经销商侧的填报；明确总部需要什么、经销商能提供什么、哪些可自动获取、哪些必须人工确认——从数据源头把口径对齐。
- **链路**（统一入口 → AI抽取校验 → 风险标记 → 人工终审）：
1. 嵌入而非重建：总部已有成熟管理系统在跑，员工和经销商都习惯了，推翻重建不现实——保留现有框架，适配已有系统、增加接口、调整流程；经销商按统一字段提交，能自动抽取的由AI完成，只需确认和补充；
2. AI抽取与校验：大模型集中处理过去最消耗人力的部分——从非结构化数据抽取信息、清洗、格式转换、识别异常；专业系统负责存储、权限和流程流转；
3. 风险标记：AI先做辅助标记、保留人的最终决策权，每处标记附带依据——历史对比、区域参考、行业规则，审核人员看得到判断逻辑；
4. 人工终审：最终判断、复杂业务决策、异常处理留给人。
- **机制**：问答硬约束——业务的人可以用大白话直接问（如"这个SKU为什么掉了"），但不是模型直接吐答案，而是帮定位到那一行原始数据，每个数字都点得开、看得见来源——溯不回去的问题，就不让它答。数据质量先建规范，再用AI处理非结构化数据，并收集正常、异常和边界案例做评估样本持续测试。
- **落地**：窄启动——第一版只做中国、只做一条产品线、只回答一个问题：这条线的钱花得值不值；就这一条线端到端做完整（数据能进来、数字点得开、结论能进周会），跑通了越南才接进来。交付五步——诊断、数据审计、窄MVP、嵌入、扩展，顺序不能乱。

#### 效果

- **量化**（原文口径限定：数字做过脱敏，量级是对的，绝对值做了处理）：市场费用问题发现率从人工审核的不到10%提高到约30%左右——不是100%自动判断，最终仍由人工确认，但审核效率明显提高。
- **人与组织**：从经验管理变成数据管理——过去海外业务管理高度依赖个人经验，换个人判断能力可能下降；AI介入后，什么数据异常、什么费用合理开始沉淀为企业能力。周会以前前一个小时在对数，现在直接从要不要动预算开始；以前说"给我一份报告"，现在直接问"这个SKU为什么掉了，是价格、铺货，还是渠道出了问题"。
- **延伸**：长期价值是建立企业的数据能力——未来进入更多国家、管理更多渠道时，手里有一套可复制的数据治理方式。

#### 教训与边界

- **弯路**：最初设想搭建专门的海外数据平台，现场走了一圈后推翻，改为在原有系统上做能力叠加；很多人认为这只是数据对接问题，进入现场后发现远比想象复杂。
- **边界**：难点不在技术层，技术大概只占20%；一张发票可能是PDF也可能是手写、折叠、模糊的图片——不针对边界情况做充分测试，模型上线后一定出问题；不要从技术出发，先问业务哪里最痛、哪里过去依靠人工经验；评判项目不看demo多炫，看客户有没有真的改变决策方式。

## 第六类　AI调度、工具算数：分析与计算自动化 {#appK-6}

这一类方案针对分析、计算类的专业工作：分析靠人写SQL跑模型，复杂计算靠老师傅经验，追问式的需求撑不住。解法方向一致——AI当调度员，理解和调度交给模型，事实与计算留给专业工具和算法，人负责最终决策；差别在于调度的对象。

### K6.1 规划研判：AI当调度员，计算留给专业工具（FDE NO.4）

#### 背景

- **企业**：城市规划（规划设计院）项目，要打交道的大约有10个部门；一期涉及大约10个部门，目前大概有20—30名专员在使用。
- **业务**：过去快速扩张时很多规划在增量空间里做选择，现在更多在已有城市空间和存量地块里找最优解，规划越做越精细、决策约束变多；领导一句"帮我看看识别下xx区域的潜力用地有哪些"，下面的人就要查资料、调数据、做空间分析、跑工具，最后才能形成报告。

#### 痛点

- **表现**：业务、数据、空间、工具四件事要连起来，还有第五件事"人"——10个部门各有专业工具、业务语义、数据规则和工作流，对同一个指标的理解也可能不一样；不理解他们的业务语言和计算规则，AI生成的东西看起来很专业、真正的规划师一看就知道不对。
- **代价**：一个人的单项分析过去约一个小时；一份跨部门完整报告通常需要3—5天，有时接近一周，大量时间耗在查资料、找规则、切换工具、重复计算、整理报告上（原文注明：这不能说明他们效率低——规划对精度要求非常高，结果必须反复核对、修改和讨论）。
- **旧办法**：规划院数字化程度并不低、不缺软件，专业软件非常复杂，规划师本身是高数字素养人群——查资料、进GIS类专业工具做空间计算，形成本部门判断，再汇总多部门分析。撑不住在数据、规则和部门不断增多——工具解决的是单个环节的计算精度，没有一个角色把业务、数据、空间和工具连接起来，跨部门、跨工具的流程靠人串联。

#### 解法

- **思路**：AI更像调度者——模型负责理解和分析，专业工具负责事实和计算，人负责最终决策。
- **前置**：先把自己逼成"半个规划师"——学厚的专业册子和术语，到不同部门把数值意义、空间计算方式、业务指标、工作流程搞清楚；再把问题缩小——从整个市缩到一个区、再缩到具体单元，只挑两条明确的业务流验证。
- **链路**（建底座 → AI调度工具 → 回显地图）：
1. 建三个底座：数据——报告关键数据尽量来自规划院真实数据并经专业计算得到，不让模型自己猜；知识——把规划规则、专业文档整理成可检索的依据（如写字楼不能建在某位置，可能碰到了历史文化保护线）；报告模板——归纳相对通用的输出结构。AI是在真实数据、专业规则和固定结构里工作，不凭空写作；
2. AI调度工具：规划师提出选址任务，AI理解意图、调用对应的数据和专业工具完成分析、把计算结果返回；高频、规则明确的任务固化成工作流，城市研判、潜力用地分析这类长尾、开放性强的问题交给Agent；
3. 回显地图：不把所有东西都变成聊天框——规划师真正工作的中心是地图，左边是筛选条件和专业工具、中间是地图、右边才是Copilot，AI的分析结果直接回显到地图上，最终决策留给规划师。
- **机制**：因数据安全要求生产环境不能随便使用国外模型，本地模型在复杂任务上效果又未达预期，采用混合部署——推理复杂场景用云模型，跑固定流程走本地模型（如Qwen7b），再用更明确的系统提示、工具封装和工程规则弥补模型能力。
- **落地**：找"执行一号位"——发起人可能是副院长，真正能协调10个部门的往往是下面负责总调度的人；某部门暂时不给数据不让项目停——少一个部门先少做一个场景，整体链路必须跑通，交付原则是"一文、一图、一表"必须出来。

#### 效果

- **量化**：过去一份跨部门完整规划报告通常需要3—5天、有时接近一周，现在在已经跑通的试点流程里，大约10—20分钟就可以形成一份能够继续推敲和交付的报告；过去约一个小时的单部门分析和表格，现在大约5—10分钟。
- **人与组织**：规划师从查资料、找规则、操作工具、整理结果里脱离，精力放在真正需要专业判断的事上；第一期陪部门梳理工作流之后，有些部门已开始自己把"识别、计算、处理、输出候选地块"这样的流程沉淀成Skill。
- **延伸**：AI有时会给出原工作流之外的潜在分析因子——判断区域经济活跃度，过去看交易、车流，AI可能提示观察停车场闸机频率、房屋空置率、人口画像，未必直接是答案，但提供了新的研究视角。

#### 教训与边界

- **弯路**：部门不一定愿意给数据和规则——有人担心上线后影响自己的岗位和价值，要数据时有人回复很慢，甚至直接说"网上都有，你们自己查"；客户想要的"AI效果"不一定真是最好的解法——"一句话出报告""万能问数""多智能体博弈"均被劝退，选址最终还是依赖明确的规则和指标计算，强行做多智能体反而结果不收敛，改为底层把专业能力封装成工具、由一个核心Agent统一调度。
- **边界**：
1. 判断一个场景值不值得用AI，看它是不是重复发生、重复成本是不是足够高、工作流能不能定义、事实和数据能不能追溯、专业工具能不能被调用；
2. 不迷信技术先进性——硬编码能解决就硬编码，任务固定用工作流，开放任务用Agent，传统算法比大模型精准就用传统算法；
3. 不要一上来做大，先找到足够小、足够真实、能闭环的场景，跑通再扩。

### K6.2 货车装载：模型调度＋算法装箱＋指导图执行（FDE NO.6）

#### 背景

- **企业**：黑河自贸区中俄跨境贸易，当地很多企业通过公路运输向俄罗斯出口机电产品。
- **业务**：跨境运输运费按"方"计算，本质是关于"车厢容积"的生意，一辆货车约110方。

#### 痛点

- **表现**："把货装满"本质是复杂的空间优化问题，不是简单装箱；俄方提供的多是车厢外部尺寸，实际可利用空间受车厢壁厚、保温层影响，往往比理论数据少5%～8%；装车主要靠人工经验，同一批货不同装车人员结果不同，整体空间利用率通常只有60%～65%左右；多车型、多货物、多辆车同时安排时，已超出人工经验能处理的范围；算得出最优解，也不代表现场能够执行。
- **代价**：
1. 一辆约110方的货车，老师傅人工装载通常要5个小时，能装到95～98方，而98方就是保本线——装不满98方就亏；
2. 每超过保本线1立方米，额外增收100美元运费——装载率不是技术指标，是利润开关；
3. 一辆货车无论装多少货都要支付同样的运输费用，只装一部分空间就发出去，剩余空间浪费、成本不降。
- **旧办法**：主要靠经验丰富的老师傅规划——根据货物尺寸、数量和过往经验判断什么货放下面、哪些可以组合摆放。撑不住在经验需要多年积累、无法复制；车型、货物、数量增加后人工很难找到最优方案；过去企业尝试过数字化工具但效果不好——只解决计算、没考虑执行，三维方案现场工人看不懂，最后回到人工经验。

#### 解法

- **思路**：大模型负责调度，专业算法负责计算，算法结果转化成工人能直接执行的装车指导图。
- **前置**：先进现场重新理解业务、技术开发放在后面——弄清工人到底怎么装、为什么这么装、哪些环节影响效率、哪些必须符合人的习惯，把装车流程拆成尺寸获取、货物整理、方案计算、调度优化、生成指导、现场执行几个步骤。
- **链路**（量尺寸 → 算方案 → 出指导图 → 现场执行）：
1. 量尺寸：车辆真实内部尺寸是计算准确性的基础，专业扫描设备成本较高、企业接受度有限，采用iPad Pro LiDAR结合激光测距，把硬件成本控制在约8500元；
2. 算方案：大模型负责理解问题、解析任务、调用装箱算法、解释结果；真正的三维空间计算由Python算法完成（高度图3D空间追踪、贪心放置、遗传算法等）——大模型在三维装箱这类复杂空间计算上难以胜任；
3. 出指导图：最初想用三维可视化系统让工人查看方案，现场发现装车环境不适合频繁操作手机或电脑，改为一张工人能直接使用的装车指导图——货物编号、摆放方向、截面示意、装载顺序；
4. 现场执行：用"截面法"按车厢截面从里向外规划装载顺序，工人只需站在车门位置操作，不需要踩踏货物进入车厢。
- **机制**：现场反馈持续回调目标——最初算法优先追求空间利用率最大化，现场反馈有些方案理论上更优但实际操作困难（要进车厢内部搬运、频繁调整货物位置），改为在效率、安全和操作便利之间找平衡。
- **落地**：测试针对长16.4米、宽2.47米、高2.67米（内净约108方）的真实运输车辆进行模拟装载，结合11种不同规格电动车产品目录，项目已完成原型验证。

#### 效果

- **量化**：原型验证口径——AI系统在不依赖老师傅的前提下，实测稳定达到约99方，逼近车厢容积上限，把原本靠老师傅5小时经验判断、结果波动的过程，压缩为分钟级、可复用的标准方案；现场执行为预计口径——人工装一车通常约5小时，引入AI规划与指导后预计可压缩到约2小时，装车效率提升约100%，同样工时内可装载的车次接近翻倍。
- **人与组织**：工人装完一车不用再等，可以立刻接着装下一车；收益三方叠加——工人同样工时装更多车、按车次计的收入直接增加，物流公司周转效率提升，货主每一车都稳定越过98方保本线，按"超1方+100美元"的计费结构，多出来的每一方都是实打实的增收。
- **延伸**：不是零和博弈里谁省了钱，而是做增量——把5小时压成2小时，多出来的车次、多出来的方，工人、物流公司、货主三方一起分；原来只有老师傅才能完成的工作，可以通过标准化流程复制。

#### 教训与边界

- **弯路**：算法结果和现场执行之间存在差距——最初追求利用率最大化的方案现场操作困难，后用截面法落地；三维可视化交互不适合装车环境，改为装车指导图。
- **边界**：
1. 最大的挑战其实来自业务方面，技术层面的问题相对更为可控；
2. 不能误以为大模型可以直接解决所有问题——三维装箱涉及复杂空间计算，大模型难以胜任；
3. AI落地要算清经济账——运费按方算、98方保本、每方增收100美元，这些商业机制直接决定装载优化的价值落点。

### K6.3 网络数据分析：拆组件重组成可反复运行的Agent系统（FDE NO.16）

#### 背景

- **企业**：美国前三大的电信运营商，客户有几十甚至上百个分析师。
- **业务**：分析师的日常工作是分析网络数据、回答"网络到底发生了什么"（如现在哪个基站坏了、为什么坏、影响多大）——过去自己写SQL、甚至建机器学习模型，从数据里找问题，再整理分析结果给经理或管理层。

#### 痛点

- **表现**：一个新的分析需求可能需要一两个人甚至两三个人一起讨论、写SQL、分析数据才能得到结果；SQL写到上百行甚至几百行中间可能出问题，后来的项目中发现过一些看起来正确、实际上取错了数据的情况；传统仪表盘适合回答预先定义好的问题，现实的分析是不断追问的。
- **代价**：
1. 分析本身太依赖人工且问题永远在变化，非常耗时间；
2. 存在人为错误；
3. 客户已有数据、有分析师、也有很多AI工具，但没有真正组合成一个可靠的业务流程——静态报表远不能满足围绕数据持续追问的交互式分析需求。
- **旧办法**：人工分析对相对固定的问题很有效、能结合业务经验判断结果，但撑不住追问式分析；客户在FDE介入前自己也搭过一个Agent——给模型一个提示词"你现在是一个数据分析师，我给你这些数据，请帮我分析"，真正跑起来结果往往不令人满意；有些方案把问题归结为"大模型本来就不确定，答案不一样很正常"——数据没变，同一个问题的答案就该一致，"能跑起来"和"可以生产使用"是完全两回事。

#### 解法

- **思路**：不做"会聊天的分析师"，把分析流程拆成组件重组成一个可反复运行、结果稳定的业务系统。
- **前置**：先搞清楚三个问题——客户到底要什么输入？最后需要什么输出？中间到底发生了什么？这三个没搞清楚，Agent写得再漂亮也没有意义。
- **链路**（拆组件 → 运行 → 稳定性标准）：
1. 拆组件：把原来的数据分析过程拆成比较细的不同组件，逐个环节考虑应该用什么方法、什么结构再重新组合，让整个Agent的输出尽可能达到客户要求的结构和质量；
2. 运行：系统理解问题→处理对应的网络数据→进行分析→给出结构化结果；
3. 稳定性标准：每一步都考虑数据是不是对的、分析过程可不可靠、输出格式符不符合要求、同一个问题重复执行结果是不是稳定——最终交付从客户角度看是"一个Agent"，实际是一个可被反复使用的系统。
- **机制**：几十甚至上百个分析师不能每人单独装一个Agent、单独维护一套东西——方案很快失控；把Agent放到云端，统一控制、监督和使用，让不同用户共同产生的数据和经验反过来提升系统，包括记忆、语义层等能力。
- **落地**：尽量不改变客户原来的工作习惯——通过网页应用、Teams、Slack或其他已有框架调用，客户继续以聊天的方式使用。

#### 效果

- **量化**：以前一个新的数据分析问题可能需要一个人甚至两三个人一起工作、按天计算；现在很多分析可以在分钟到小时级别内跑完，先得到一份比较完整的数据分析结果，再由人工做最后的质量确认。
- **人与组织**：分析师可以站在AI已经完成的结果上继续判断，不需要从零开始；人工审核没有彻底拿掉；AI系统还可以减少人工分析中一些容易出现的错误；不能简单理解成"AI替代了几个分析师"。
- **延伸**：交互方式从"提前把问题定义好然后给你看答案"的仪表盘，变成可以围绕数据继续追问——对电信网络这种数据量大、问题变化快的业务，比单纯生成一张报表更有价值。

#### 教训与边界

- **弯路**：客户自搭的"你是数据分析师"提示词Agent结果不令人满意；调试成本差距大——一个不知道怎么做Agent的团队可能为了调试一个东西花几千美元，一个真正有经验的人可能用十几、二十美元级别的成本就能完成同样的调试。
- **边界**：
1. 最大挑战是很多AI演示不会暴露的稳定性、准确性、成本、规模化——第一阶段问什么都能答、很容易成功，进入生产环境后，同一问题反复问答案是否一致、SQL有没有写错、用户从一个人变成几十上百个时成本还能不能接受，这些才是决定Agent能不能落地的地方；
2. 通过系统设计把模型随机性放进相对可控的业务流程（原文比喻：汽油本身不稳定，但汽车工程的意义就是让汽油安全、稳定地驱动车辆）；
3. 成本不止"调用模型多少钱"，还有长期运行成本——架构设计得不好就像一辆漏油的车，根本不用谈省油。

### K7.1 超市自主采购：买什么何时买向谁买，整段交给AI（斯坦福·超市采购）

#### 背景

- **企业**：区域连锁超市，约二十来家门店（问题段另述数千SKU、25家店，两处口径不同，均照原文录）。利润率约为行业基准的一半，对供应商几乎没有议价能力——与利润丰厚、采购力巨大的市场领导者形成对照。
- **业务**：采购职能由人工采购员独扛——凭手感、供应商关系和手工拼凑的数据决定买什么、何时买、从哪家供应商买；库存、供应商目录、销售历史分属多个系统，靠人肉拼接，采购员本身就是跨系统的集成层。

#### 痛点

- **表现**：三个互锁难题：浪费——生鲜在货架上过期、季令商品订量错误、促销品卖不动；缺货——空货架丢的不只是一单生意，顾客开车去了对手那儿可能就不回来了；采购时点——人工凭手感做决策。
- **代价**：超市经济学不饶人：利润薄、浪费持续、缺货永久丢客；在利润率只有行业基准一半、采购力为零的处境下与巨头同场竞争。
- **旧办法**：人工采购员独扛采购职能。撑不住的判定很直接：一个人不可能对数千个SKU、25家门店做优化。

#### 解法

- **思路**：部署完全取代人工采购职能的AI系统——不辅助人、不生成供审阅的建议，而是自主做采购决策：买什么、何时买、从哪家供应商买。
- **链路**（数据平台 → 需求预测 → 自主采购代理）：
1. 数据平台：从多个系统抽取库存、销售、供应商数据——此前这个跨系统取数的集成层就是人；
2. 需求预测：预测到门店与SKU粒度的销售；
3. 自主采购代理：决定买什么、何时买、向谁买，同时对所有门店、每家店的每个商品做持续决策。
- **机制**：接管整个职能而非单个任务；把以前靠直觉串联的多步决策——预测需求、查库存、算供应商交期、权衡浪费与缺货——连成系统链条；跨系统取数无需人工编排。AI能自我评估，因为结果可测：商品是卖了、过期了、还是断货了。

#### 效果

- **量化**：浪费降低40%；缺货降低80%；EBITDA利润率翻倍。项目负责人的说法：市场领导者利润率高得多，这帮人规模超小、采购力跟大玩家比是零，但他们做得几乎一样好——靠的就是没有浪费。
- **人与组织**：人工采购员岗位被AI工具整体取代；原文未提该人员的去向与安置。
- **延伸**：小零售商对抗巨头的路径——agentic AI把"智能"变成"规模"的替代品。

#### 教训与边界

- **边界**：适用任务画像——对规则引擎太复杂、对人工太重复，且有清晰成功标准与可恢复错误。样本局限（作者注）：数据采集期为2024年8月至2025年1月，agentic技术仍在早期，样本中仅20%的实施属agentic工作流、多数组织在试验而非规模化；样本中agentic实施的中位生产力增益为71%，高自动化为40%。

### K7.2 呼叫中心：AI嵌进产品自己关单，从卖坐席转卖结果（斯坦福·呼叫中心）

#### 背景

- **企业**：呼叫中心即服务公司（CCaaS），为企业客户提供传统呼叫中心服务——接听来电、路由咨询、管理工单队列。
- **业务**：按坐席收费（seat-based pricing），人工坐席接听、路由、管理工单。

#### 痛点

- **表现**：市场被AI原生竞争者改写——企业客户开始把AI能力视为标配而非溢价附加项；AI原生创业公司从第一天起就提供智能路由、自动解决、实时分析。
- **代价**：传统按坐席收费加人工坐席的模式两头受压：对手每次交互能交付更多价值；AI让客户所需坐席数下降，直接侵蚀定价根基。原文定调：挑战不是运营效率，是战略相关性。
- **旧办法**：卖坐席加人工接听、路由、管工单。撑不住的原因：AI原生对手单次交互交付价值更高且自带智能路由、自动解决、实时分析；坐席需求本身被AI压缩，按坐席收费的商业模型随之瓦解。

#### 解法

- **思路**：不是用AI给人工坐席提速，而是把agentic AI直接嵌入公司产品本身——AI端到端解决工单，真正关单。
- **链路**（嵌入产品 → 端到端解决 → 自主任务完成）：
1. 嵌入产品：管理层把agentic AI直接嵌入公司产品本身；
2. 端到端解决：重设计服务——AI不只接电话、答问题，而是把工单解决到底；
3. 技术路线：采用能编排完整解决流程的agentic AI框架，超越copilot式辅助，进入自主任务完成。

#### 效果

- **量化**：新项目赢单——结果框口径为20+（attributed to AI），正文另述赢得三十个新项目，不是因为公司更便宜，而是因为比仍按传统模式运营的对手更有能力，两处口径不同，均照原文录；独立技术评估将其排入客户关系AI能力前四，其余三家全是AI原生公司；持续赢得新客户，每个单子都有AI——没有不带AI的项目。
- **人与组织**：竞争参照系被换掉——一家传统呼叫中心从此被拿去与AI原生创业公司对标，而不再与其他传统玩家比。
- **延伸**：定价模型开始从卖坐席转向卖结果；AI能力成为产品本身，而非给老产品降本的工具；同一套技术栈本可用于裁员或压低单票成本，却被用于重塑市场位置——原文小结：三件变化都与效率无关。

#### 教训与边界

- **边界**：为效率部署的AI省钱，部署进产品的AI改变竞争位置；差别不在技术，在问的问题——不是"怎么降成本"，而是"怎么赢下以前赢不了的单"。附PE合伙人观点：中小公司拿到对的能力后在AI革命中位置很好——决策更快、遗留系统少、以前不知怎么用的非结构化数据现在能用、缺的资源可被AI增强。

## 第八类　合规上云与模型架构 {#appK-8}

这一类方案针对两道底层难题：数据不能出域，但云上的模型更强；不想把命押在一家模型供应商手里。解法方向一致——用架构解题：出口清洗换合规，模型网关换选择权。

### K8.1 合规上云：出口清洗＋假值顶替＋回程重组（斯坦福·零售银行）

#### 背景

- **企业**：美国大型零售银行，服务数百万客户，渠道含移动App、线下网点、呼叫中心；受联邦银行业监管，因过往合规问题背负监管同意令（consent orders），形成深度风险厌恶文化。
- **业务**：计划在手机App里部署AI虚拟助理，承接客户服务。

#### 痛点

- **表现**：技术政策禁止使用任何位于公司防火墙之外的软硬件，而现代AI全面云化——政策使云端AI无法落地。
- **代价**：政策不松，AI虚拟助理上不了线；真正难的不是技术方案，而是改动被既往同意令塑造的风险厌恶文化。
- **旧办法**：旧政策是"一切必须在防火墙内"。撑不住的原因：现代AI是云端的，两条线直接冲突，必须找到既合规又能用云的架构。

#### 解法

- **思路**：防火墙政策不必推翻——真值不出防火墙，云端只见清洗后的数据，用数据保护架构换取合规与用云并存。
- **前置**：多年的安全投入——这是大规模处理敏感金融数据、做触碰客户账户的AI服务的前提底座，大头成本在首次部署前已付掉。
- **链路**（出口清洗 → 假值顶替 → 云端判意图 → 回程重组）：
1. 出口PII清洗：客户话术在离开防火墙前剥离姓名、账号、金额；
2. 合成数据替换：外送处理期间用假值顶替真值；
3. 意图识别外置：云端模型判定客户意图并选择相应工作流；
4. 回程重组：回到内部后把真实值重新插回，再呈现给客户。
- **机制**：送给Google Cloud平台的是清洗后的最小必要集合——换上假名字、假金额，模型照样能识别意图；回程时再把这一切重新拼回响应（高管引语）。
- **落地**：虚拟助理上线之后，下一阶段已排定用agentic AI做预约排程。

#### 效果

- **量化**：该渠道成为成本最低的可服务渠道（Lowest to serve）；呼叫拦截（Call containment）48-72hr reduction（原文口径如此照录）。
- **延伸**：文化上的松动反过来给了比竞争对手更快的上市速度优势。

#### 教训与边界

- **边界**：
1. 安全是基础设施不是overhead：没有多年安全投入攒出的底座，做不了触碰客户账户的AI服务；
2. 安全税前置：首次部署付掉大头后，后续用例复用同一套管线、云合同与合规归档系统；
3. 如今已有多款高能力开源方案，把AI功能部署在内部、不动既有政策也可能达到类似效果，属可行备选；
4. 风险厌恶文化是最难的屏障——改文化才是真挑战，技术反而不是。

### K8.2 多模型网关：不赌供应商，按查询自动路由（斯坦福·客户支持）

#### 背景

- **企业**：通信科技公司（企业级）。原文未提员工与工单规模细节。
- **业务**：客户支持团队承接工单，坐席按传统方式招聘扩容。

#### 痛点

- **表现**：客户支持量的增长快过招聘坐席的能力；原文定调——真正的技术难点不是做一个聊天机器人，而是建一套能把查询路由到最优模型、按成本/准确性/延迟优化、避免供应商锁定、并能随新模型发布持续变好的基础设施。
- **旧办法**：扩招坐席扩容支持团队——撑不住在于量增快过招聘；模型侧的对照旧法是选定单一模型供应商，其陷阱为供应商锁定、一次性全局成本决策、模型换代要重构。

#### 解法

- **思路**：不赌任何一家模型供应商——把"选型"从人的战略决策下沉为基础设施里每条查询的自动路由。
- **前置**：不选定单一模型供应商，先建multi-LLM网关，把模型选择从应用层抽象掉。
- **链路**（查询进网关 → 四维路由 → 分级应答 → 持续自优化）：
1. 查询进入：每条客户查询先过网关；
2. 四维路由：网关按成本、延迟、相关性、准确性四个优化维度路由每条查询；
3. 分级应答：常规客服查询任何前沿模型都够用；需要深检索或高准确率的复杂查询，路由给更强的模型；
4. 持续自优化：系统随新模型发布持续变好，不需要任何人再做战略性的"模型选型"决策。
- **机制**：多模型混用——Claude、OpenAI、Llama都在用，有时也用Bedrock（Head of Operations引语）；路由与优化由网关自动完成，人的"模型选型"决策不再存在。

#### 效果

- **量化**：工单拦截率82%；解决率71%；坐席生产力提升40%+；支持编制缩减32%。
- **人与组织**：支持团队编制减32%（原文未提人员安置方式）；模型选型决策从人的战略决策移入基础设施自动完成。
- **延伸**：避开三个架构陷阱——供应商锁定（任何厂商的进步都能直接吸收，无需重构）、成本优化（按查询粒度优化，而非一次性全局选型）、面向未来（模型进步的技术与成本红利被基础设施自动吸收）。

#### 教训与边界

- **边界**：
1. 模型抽象比模型选型更重要：上述业务结果由大规模自动化客服驱动，multi-LLM网关主要在系统内优化成本与延迟；
2. 常规查询任何前沿模型皆可，复杂查询才需要更强模型——这是模型选择的商品化边界。

## 第九类　组织与人的解法 {#appK-9}

### K9.1 研发AI转型：把个人用法统一成团队协作方式（FDE NO.7）

#### 背景

- **企业**：基金公司（偏基金投研类，围绕股票、汽车等领域开展基金管理业务）；对象是一支需求变化非常快的内部研发团队——内部产品经理或业务部门一天可能就提出好几个需求；客户已确定采用阿里的相关能力。
- **业务**：研发协作围绕飞书文档PRD展开——产品经理写PRD，开发按文档开发，角色按原有分工推进；AI Coding工具出现后，有人用Codex、有人用Claude Code，各自提效。

#### 痛点

- **表现**：大家都会用AI，但企业很难让大家一起用——每个人都觉得自己的工具最好。认知没有统一，工具和方法没有统一，管理层想调整研发角色和流程却没有现成答案；转向Markdown等多文件协作后，十几份文档怎么拆、各角色各写什么、同时修改怎么避免冲突，原有角色边界不一定还能沿用。原文对AI价值形态的界定：把研发人员每天能完成的功能点从三个提高到十个，与"原来一年做完的项目现在半年做完"的传统想象并不相同。
- **代价**：个人习惯越成熟，企业想统一工具阻力越大；管理层要的不只是几个员工个人效率提升——希望AI成为组织能力，不再只是散落在员工电脑里的个人工具。
- **旧办法**：个人自发用AI工具提效——个人只对自己的效率负责，这个阶段其实没有什么问题。撑不住的是从"个人提效"走向"团队提效"：围绕飞书文档PRD的协作方式与多文件协作不匹配，文档拆分、角色分工、修改冲突都不是学会一个AI工具之后自然就会解决的。过去的方法不是"错误"，是适应原来研发模式的成熟方法；研发方式变了，流程、文档和角色分工需要重新调整。

#### 解法

- **思路**：AI Coding落地的卡点不在工具而在组织——把散落在员工电脑里的个人用法，变成企业共同的研发协作方式。
- **前置**：把不同角色的需求拆开看——企业负责人关注转型能不能发生，研发人员关注工具能否提高自己效率，产品经理关注流程怎么变，HR关注培训每天能获得什么；不轻信前期调研——企业自述能力水平经常不等于现场真实水平，靠真实操作、快速原型和现场交流验证。
- **链路**（故事线培训 → Spec文档从0到1 → 三期迭代）：
1. 培训做成完整业务故事线：五天半不是只讲工具——从为什么转型、工具怎么进入原有流程、角色怎么变化，到沉淀成企业自己的方法；既在讲也在观察，既是培训也是咨询；
2. Spec文档从0到1：围绕一份PRD的分工不能直接套用到多文档协作，行业里没有成熟统一标准可照搬——不把设计当"标准答案"扔给客户，而是不断拆解、逐步抛出、跟客户确认、根据反馈继续调整；
3. 三期迭代：第一期最重要的价值是真正看到企业现场什么样，第二期按第一期经验继续调整；后续业务人员、产品经理逐渐进入，项目从单纯研发培训变成更完整的组织转型。
- **机制**：先把整个链路跑起来，再按真实反馈不断迭代，第一次不必追求100分；现场发现的问题继续往后调整。
- **落地**：共做三期、每期五天半线下培训；Spec文档和相关方法沉淀在企业内部继续复用，不再依赖某一个人现场演示。

#### 效果

- **量化**：这家基金公司没有向作者开放可以对外披露的完整ROI数据。另一个制造业客户出现了比较明确的短期数据——三个小组使用这套Spec Coding方法和模板后，统计显示写代码的时间节省约1/3，写文档的时间节省一半多，测试时间基本持平；这是客户在短期几天内做的内部统计，可以作为真实反馈，但不应被理解成长期、完整的ROI结论——真正有价值的效果评估还需要持续两周、一个月甚至更长时间。
- **人与组织**：AI从个人能力（每人有自己的方法和工具）变成团队共同的研发流程，不再只是"某个开发人员会不会用"的问题；企业完成了从"大家各自使用AI"到"形成一套共同使用AI的方法"的变化。
- **延伸**：Spec Coding方法和模板在另一个制造业客户复用并产生短期统计数据。

#### 教训与边界

- **弯路**：前期调研经常失真——有一次提前了解到客户团队AI Coding能力比较深，准备了很多高阶内容，到现场发现大家连一些基础问题都没有解决，只能现场降级从基础开始；现场能力本身就是FDE的重要组成部分。另外担心自己整理的方法刚拿出来就被客户否定——办法是把不确定性暴露出来，通过小步验证降低风险，不假装自己已经知道答案。
- **边界**：
1. AI发展太快而行业标准还没有跟上——不能因为没有标准就不做，也不能因为是技术人员就假设自己一定是对的；
2. 企业一开始就"大投入"反而危险——一上来买一体机、做模型微调、强行推翻原有全部工作流；业务能用轻量级方式（API、SaaS或Agent）先跑起来验证价值的，先验证，投入由轻到重；
3. AI使用水平很难通过问卷准确判断——快速做原型、快速跑一遍真实流程，哪怕第一次只有七八十分，也比把方案讨论到100分再开始更有价值；
4. "我要做AI转型"这句话本身没法指导落地——个人提效、团队提效、研发流程重构，不同目标对应完全不同的方案。

### K9.2 招聘管线重造：CEO亲自抓，先修流程再上AI（斯坦福·招聘）

#### 背景

- **企业**：翻译服务公司（专业服务行业，中型市场规模）。具体人数原文未提。
- **业务**：公司经营翻译服务，业务扩张需要持续招聘配员，含小语种和方言岗位。

#### 痛点

- **表现**：招聘流程是公司最大的成本汇聚点和业务扩张的战略瓶颈——候选人录入慢、人员流失高、小语种和方言岗位难配员、筛选质量不稳定；招聘团队每天被申请流淹没且不断加剧（"I'm drowning"，高管原话）。
- **代价**：限制了公司能多快增长（具体金额原文未提）。
- **旧办法**：这是该公司第二次尝试AI招聘。第一次失败有两个原因：筛选算法没有考虑偏差；假设AI会修复坏流程，而没有解决底层的工作流问题。

#### 解法

- **思路**：先修流程再上AI，所有权归CEO——同一家公司、同一职能、同一目标，第一次与第二次的差别不在技术。
- **前置**：CEO亲自接管所有权而非委派给CTO，项目有高管可见度，每周check-in快速清除瓶颈；先绘制整个招聘工作流，识别真正痛点在哪。
- **链路**（超个性化筛选 → 自动首轮视频面试 → 结果反馈回路）：
1. 超个性化筛选：按语言和方言做筛选；
2. 自动首轮视频面试：带偏差缓解评估；
3. 反馈回路：连接招聘结果与筛选标准——系统学习哪些候选人信号预示成功。
- **机制**：学习回路持续从招聘结果反推筛选标准；每周check-in清除瓶颈。
- **落地**：约一个月建成（Time to build约1个月）。

#### 效果

- **量化**：单个岗位处理时间从3小时缩至3分钟（3 hrs → 3 min）；录入效率+83%；筛选效率+79%；候选人转化+75%。Key Lessons口径：第二次用一个月交付83%效率提升。
- **人与组织**：采用容易——招聘团队不需要被说服，需要被救援；CEO亲自当owner带来高管可见度，瓶颈被快速清除。
- **延伸**：系统从招聘结果反推筛选标准，持续学习哪些候选人信号预示成功。

#### 教训与边界

- **弯路**：第一次AI尝试失败——未考虑筛选算法偏差，且假设AI能自动修复坏流程而不解决底层工作流问题。
- **边界**：
1. 先修流程再上AI：AI放大它所应用的任何流程——流程坏了，AI让它更快地变得更坏；
2. 瞄准真实痛点：采用容易是因为用户急需解脱；
3. 所有权归属：CEO亲自接管而非委派CTO，是第二次成功的条件之一。

### K9.3 增益再投资：节省转投路线图，编制零裁减（斯坦福·工程）

#### 背景

- **企业**：教育科技公司，数千名员工，其中200余人属技术条线、100余名工程师；跨受监管行业提供继续教育与职业认证课程。
- **业务**：技术团队手工编码开发产品；课程内容生产由主题专家（SME）亲笔起草。

#### 痛点

- **表现**：技术团队纯手工编码（试点证实工程环节有20-30%的时间精力可省）；公司背负大量产品积压；领导层在PE压力下需要展示回报。
- **旧办法**：工程靠人力编码、内容靠SME亲笔起草。撑不住的量化证据即解法后的落差：GitHub Copilot与Cursor试点省下20-30%时间精力，内容生产重构产生数百万美元级节省（原文未另行展开旧法失效叙事）。

#### 解法

- **思路**：生产力增益是战略选择题而非自动结果——同一笔增益可以支撑裁员，也可以支撑加速路线图；本案把节省转投AI与路线图，工程线不减员。
- **前置**：CTO制定三支柱AI战略——工程生产力工具、客户体验改进、AI差异化产品。
- **链路**（六个月试点 → 内容重构 → 编制之争裁定 → 节省落袋转投）：
1. 工程试点：工程团队用GitHub Copilot与Cursor跑六个月试点——早期即省20-30%时间精力，随提示词与信心提升还有上行空间（CTO引语）；
2. 内容重构：AI起草内容，SME从起草者转为human-in-the-loop审校者；
3. 编制之争：CEO与COO在PE压力下倾向降本裁员，CFO起初不信AI能产生净节省，CTO主张加速；最终裁定工程线选择加速而非裁员——节省用于加速路线图，不减员；
4. 节省落袋并转投：在2025年预算中削减若干部门预算、再投入AI，真实兑现节省；最大节省来源是SME内容生产重构（CTO引语）。
- **机制**：AI起草、SME审校的分工持续运转；节省再投入AI开发。
- **落地**：六个月试点先行，节省在2025年预算周期落袋并转投。

#### 效果

- **量化**：工程生产力省时20-30%；开发成本数百万美元级节省（Millions in savings）；工程编制零裁减（No reduction）；节省再投入AI开发。
- **人与组织**：SME角色从起草者变为审校者；决策层三种立场（CEO/COO促裁、CFO存疑、CTO主战加速）以加速路线收场；PE回报压力被"再投资"路径化解。
- **延伸**：节省未换成人头，而是换成更快的产品路线图——shipping features faster换取更多收入。

#### 教训与边界

- **边界**：
1. 生产力增益带来的是战略选择而非自动结果：同一笔增益既可支撑裁员、也可支撑加速路线图，取决于公司优先近期降本还是长期增长；
2. 前瞻性警告（作者注）：以上发现来自截至2025年初的回溯性数据，样本中主导的"再部署与加速"模式未必随AI能力提升与经济压力加剧而延续；Brynjolfsson、Chandar与Chen（2025）分析ADP覆盖数百万美国劳动者的高频工资单数据，发现AI暴露职业中22-25岁早期职业者就业自2022年末起相对下滑16%；Anthropic补充研究未发现系统性失业上升，但AI暴露领域年轻员工招聘已放缓；"我们观察到的45%裁减率（样本口径）可能是地板，不是天花板。"

### K9.4 参见｜执行一号位与容错交付（FDE NO.4，主条目K6.1）

复杂组织里真正能协调各部门的是"执行一号位"——项目发起人可能是副院长，能协调十个部门的往往是下面负责总调度的人，先跟这个人聊透。某部门暂时不给数据，不让项目停：少一个部门先少做一个场景。交付原则是"一文、一图、一表"必须出来——不把每个环节设计成缺一不可，否则一个部门不配合整个项目就被拖死。

### K9.5 参见｜先解决小麻烦破冰（FDE NO.12，主条目K3.4）

不讲"AI转型"大词，先解决眼前小麻烦建立关系——生图要写很长的提示词、生成完还有水印要再处理。基层员工怕被取代，情绪不解决，拿到的需求可能是假的、上线没人用。

### K9.6 参见｜知识萃取与组织配套（FDE NO.14，主条目K1.6）

项目按"IT部门牵头的技术项目＋人事部门牵头的组织转型项目"双线定位，第一年IT牵头遇到瓶颈后，改由人事牵头、从全员培训重新推进。培训之后，负责行政物品的同事自己用提示词做出了补货Agent——在企业内部培养出自己的AI使用者，比外部团队替他做一个更重要。

### K9.7 参见｜一把手工程与人员安置（FDE NO.17，主条目K3.1）

岗位从三五人变一两人的消息一出，员工第一反应是担心被优化——立项前就要和企业负责人谈定释放的时间往哪转，裁人不是选项；这类转型必须是一把手工程。

### K9.8 参见｜自建团队，能力留下（FDE NO.18，主条目K5.2）

外部FDE不应永远是企业的拐杖——第一阶段之后建议董事长扩充内部团队，企业拿出20个编制，FDE参与人员招聘和团队框架建设；项目从帮企业做几个AI应用，变成帮企业建立继续往前走的能力。

### K9.9 参见｜Agent入群发现真问题（FDE NO.19，主条目K2.5）

把一个Agent放进业务群，它待了两三周，持续收集业务上下文、不急着解决问题，过一段时间总结：最近业务里有哪些问题、哪些值得沉淀、哪些可能被AI解决——最后由它自己从真实业务沟通中定位到包装审核这个真问题。外部人一直待在群里，业务同学会有压力；Agent相对隐形。

### K9.10 参见｜AI冠军、公司OKR与演示日（斯坦福·半导体现场服务，主条目K1.3）

需要跨部门采纳时：每个部门设一名AI冠军带动同侪；同级压力不够就升级到CEO、把AI采纳写进公司OKR；办AI演示日，CEO到场发奖——传递"这是公司战略、不是IT实验"的信号。部门级授权到顶了，跨职能的事要公司级支持。

### K9.11 参见｜释放容量明示去向（斯坦福·安全运营，主条目K2.7）

"AI替代的是你不用再招的人"——4.5个全职当量的释放容量，明明白白指向威胁狩猎、安全架构、能力建设；什么工作消失、什么留下、什么新工作出现，说清楚之后，恐惧就消散。
